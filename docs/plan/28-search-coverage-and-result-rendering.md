# 28. 검색 본문 커버리지와 결과 렌더링

21번 계획의 후속입니다. 검색 엔진 교체가 아니라, 현재 JSON 검색의 커버리지와 렌더링 비용을 다룹니다.

## 현재 동작

- `src/lib/searchIndex.ts`는 글 1편을 레코드 1건으로 만들고, 발췌는 480자(`EXCERPT_LENGTH`), 본문 검색 텍스트는 5,000자(`SEARCH_TEXT_LENGTH`)까지만 담습니다. 따라서 **5,000자를 넘는 글의 뒷부분은 검색되지 않습니다.**
- 전체·카테고리·코드 인덱스를 두 글자 이상 입력할 때 지연 로드하고, 받은 인덱스를 경로별로 재사용합니다.
- 2026-10-07 브라우저 벤치마크 측정값(현재 506편): `search.json` 3,432,231바이트, `ETF` 질의 cold 147.80ms, 결과 243건 렌더 시 DOM 3,215노드, warm p50/p95 30.30/33.80ms.
- 같은 벤치마크의 2,000편 합성 가정: DOM 11,402노드, `ETF` warm p95 298.40ms, `반도체` warm p95 386.10ms.
- 2026-10-07 Pagefind 비교 결론은 **교체 보류**입니다. 한국어 결과 수와 코드 검색 보존, 질의별 전송량 때문입니다. 이 계획은 그 결론을 유지합니다.

## 목표

1. 긴 글의 뒷부분도 검색되게 합니다.
2. 결과가 많은 질의에서 렌더링 비용 상한을 둡니다.
3. 인덱스 크기 증가를 측정해 예산을 넘으면 중단할 수 있게 합니다.

## 범위

- 글 단위 레코드를 heading 단위 섹션 레코드로 확장하고, 결과에서 섹션 앵커로 이동
- 결과 렌더 개수 상한과 `더 보기`
- 인덱스 크기·질의 지연 재측정
- 검색 엔진 교체, 랭킹 가중치 전면 재설계는 포함하지 않음

## 설계 방향

- 섹션 레코드는 글 메타데이터(제목·카테고리·slug)를 중복 저장하지 않고 글 레코드를 참조합니다. 중복 저장은 인덱스 크기를 글 수에 비례해 늘립니다.
- 섹션 단위로 쪼개면 레코드 수가 늘지만 레코드당 텍스트는 짧아집니다. 전체 크기 변화는 1단계에서 먼저 측정합니다.
- 결과 목록은 상한까지만 DOM을 만들고, 나머지는 사용자가 요청할 때 이어서 렌더링합니다.
- 코드 검색(`code-search.json`)의 현재 동작은 그대로 둡니다.

## 중단 조건

다음 중 하나라도 발생하면 섹션 인덱스를 되돌리고 글 단위 레코드를 유지합니다.

- `search.json`의 gzip 추정 크기가 현재 대비 1.5배를 초과
- 현재 글 수에서 `ETF`·`반도체` 질의의 warm p95가 현재 측정값보다 악화
- 같은 질의에서 기존보다 관련도 낮은 결과가 상위에 올라오는 사례가 재현

## 구현 단계

1. [미착수] 현재 인덱스의 글 길이 분포와 5,000자 초과 글 수를 측정해 실제 손실 범위를 기록합니다.
2. [미착수] 섹션 레코드 생성 함수와 단위 테스트를 추가하고, 인덱스 크기 변화를 `report:search-size`로 비교합니다.
3. [미착수] 결과 렌더 상한과 `더 보기`를 먼저 적용합니다. 인덱스 변경과 분리된 커밋으로 둡니다.
4. [미착수] 섹션 결과에 heading 앵커 링크를 연결합니다. 앵커는 22번 계획의 heading ID 검사와 같은 규칙을 씁니다.
5. [미착수] 브라우저 벤치마크를 재실행해 전후 수치를 문서에 기록합니다.
6. [미착수] 중단 조건에 걸리면 되돌리고 결과를 기록합니다.

## 테스트 설계

- heading이 없는 글, heading만 있고 본문이 없는 글, 중복 heading 텍스트 처리
- 5,000자를 넘는 글의 마지막 단락 검색어가 결과에 포함되는지 확인
- 섹션 레코드가 같은 글을 중복 결과로 노출하지 않는지 확인
- 결과 상한 적용 시 총 결과 수 표시가 정확한지 확인
- 코드 블록·수식·한국어 부분어 검색의 기존 동작 회귀 확인
