# 28. 검색 본문 커버리지와 결과 렌더링

21번 계획의 후속입니다. 검색 엔진 교체가 아니라, 현재 JSON 검색의 커버리지와 렌더링 비용을 다룹니다.

## 현재 동작

- `src/lib/searchIndex.ts`는 글 1편을 레코드 1건으로 만들고, 발췌는 480자(`EXCERPT_LENGTH`), 본문 검색 텍스트는 5,000자(`SEARCH_TEXT_LENGTH`)까지만 담습니다. 따라서 **5,000자를 넘는 글의 뒷부분은 검색되지 않습니다.**
- 전체·카테고리·코드 인덱스를 두 글자 이상 입력할 때 지연 로드하고, 받은 인덱스를 경로별로 재사용합니다.
- 2026-10-07 브라우저 벤치마크 측정값(현재 506편): `search.json` 3,432,231바이트, `ETF` 질의 cold 147.80ms, 결과 243건 렌더 시 DOM 3,215노드, warm p50/p95 30.30/33.80ms.
- 같은 벤치마크의 2,000편 합성 가정: DOM 11,402노드, `ETF` warm p95 298.40ms, `반도체` warm p95 386.10ms.
- 2026-10-07 Pagefind 비교 결론은 **교체 보류**입니다. 한국어 결과 수와 코드 검색 보존, 질의별 전송량 때문입니다. 이 계획은 그 결론을 유지합니다.

## 목표

1. 긴 글의 뒷부분도 검색되게 합니다.
2. 결과가 많은 질의에서 렌더링 비용 상한을 둡니다.
3. 인덱스 크기 증가를 측정해 예산을 넘으면 중단할 수 있게 합니다.

## 범위

- 글 단위 레코드를 heading 단위 섹션 레코드로 확장하고, 결과에서 섹션 앵커로 이동
- 결과 렌더 개수 상한과 `더 보기`
- 인덱스 크기·질의 지연 재측정
- 검색 엔진 교체, 랭킹 가중치 전면 재설계는 포함하지 않음

## 설계 방향

- 섹션 레코드는 글 메타데이터(제목·카테고리·slug)를 중복 저장하지 않고 글 레코드를 참조합니다. 중복 저장은 인덱스 크기를 글 수에 비례해 늘립니다.
- 섹션 단위로 쪼개면 레코드 수가 늘지만 레코드당 텍스트는 짧아집니다. 전체 크기 변화는 1단계에서 먼저 측정합니다.
- 결과 목록은 상한까지만 DOM을 만들고, 나머지는 사용자가 요청할 때 이어서 렌더링합니다.
- 코드 검색(`code-search.json`)의 현재 동작은 그대로 둡니다.

## 중단 조건

다음 중 하나라도 발생하면 섹션 인덱스를 되돌리고 글 단위 레코드를 유지합니다.

- `search.json`의 gzip 추정 크기가 현재 대비 1.5배를 초과
- 현재 글 수에서 `ETF`·`반도체` 질의의 warm p95가 현재 측정값보다 악화
- 같은 질의에서 기존보다 관련도 낮은 결과가 상위에 올라오는 사례가 재현

4. [완료] 본문에서 일치한 결과는 `/blog/<slug>/#<anchor>`로 연결됩니다. 앵커는 Astro가 렌더링한 heading slug를 그대로 쓰므로 22번 계획의 heading ID 검사와 같은 값입니다. 소스의 heading 수와 렌더링된 heading 수가 다르면(setext·HTML heading 등) 해당 글의 앵커를 모두 버려 잘못된 섹션을 가리키지 않습니다.

## 테스트 설계

- heading이 없는 글, heading만 있고 본문이 없는 글, 중복 heading 텍스트 처리
- 5,000자를 넘는 글의 마지막 단락 검색어가 결과에 포함되는지 확인
- 섹션 레코드가 같은 글을 중복 결과로 노출하지 않는지 확인
- 결과 상한 적용 시 총 결과 수 표시가 정확한지 확인
- 코드 블록·수식·한국어 부분어 검색의 기존 동작 회귀 확인

### 2026-10-18 구현 결과 (전체 단계)

측정은 모두 현재 글 수(506편) 기준입니다.

| 항목 | 이전 | 이후 |
| --- | ---: | ---: |
| 색인된 본문 평문 | 1,594,267자 (77.8%) | 2,057,801자 (100%) |
| `search.json` | 3,431,932 B (3.27 MiB) | 4,455,007 B (4.25 MiB) |
| `search.json` gzip | 926,921 B | 1,242,212 B (1.34배) |
| `ETF` cold 첫 결과 | 147.80 ms | 124.70 ms |
| `ETF` warm p50/p95 | 30.30 / 68.40 ms | 7.50 / 9.50 ms |
| `반도체` warm p50/p95 | 40.10 / 46.60 ms | 8.20 / 9.60 ms |
| 인덱스 heap | 14.19 MiB | 18.14 MiB |

- 앵커는 423편에 5,495개가 생성되었습니다. 나머지 83편은 heading이 없거나 heading 수가 일치하지 않아 앵커를 싣지 않았습니다.
- 중단 조건 확인: gzip 1.34배(1.5배 이내), p95 개선, 표본 질의 10개 중 9개의 상위 5건이 동일했습니다. 남은 1개(`인플레이션`)는 동점 글 사이의 순서 교체이며 관련도가 낮은 결과가 올라온 사례는 아닙니다. 일치 건수는 전반적으로 늘었습니다(`RAG` 55→69, `인플레이션` 72→80).
- 성능 경위: 1차 구현은 모든 일치 결과에 앵커를 계산해 warm p50이 269 ms까지 악화됐습니다. 원인은 두 가지였습니다. (1) 결과마다 본문 전체에서 위치를 다시 찾았습니다 → 렌더링되는 결과에만 앵커를 계산하고, 이미 정규화해 캐시된 본문에서 `indexOf`로 찾도록 바꿨습니다. (2) `findSearchMatchRange()`가 본문 전체에 대해 문자 단위 오프셋 표를 만들었습니다 → 정규화가 길이를 바꾸지 않는 경우(대부분)에는 표를 만들지 않는 빠른 경로를 넣었습니다. 그 결과 커버리지를 29% 늘리면서도 warm 질의는 이전보다 3~4배 빨라졌습니다.
- 앵커 오프셋은 발췌 경계에서 공백이 정리되며 한두 글자 어긋날 수 있습니다. 섹션 길이에 비해 무의미한 차이입니다.
- 스니펫은 설명·heading·본문 순서로 먼저 일치한 곳에서 만들고, 앵커는 본문에서 처음 일치한 섹션을 가리킵니다. 질의가 설명에서만 일치하면 스니펫과 앵커의 출처가 다를 수 있습니다.
- 벤치마크 표의 `ETF results` 열은 렌더링된 결과 수(20)를 보고합니다. 전체 일치 수와 다르므로 2026-10-07 이전 측정값과 직접 비교하지 마십시오.
- 검증: `npm test` 298개 통과(섹션·앵커 테스트 15개 추가), `npm run check` 0 errors, `npm run build` 성공, `npm run check:build-artifacts` 통과, `npm run test:e2e` 11개 통과(앵커 링크 테스트 1개 추가), `npm run format:check` 통과.
- 기존 e2e 4곳은 결과 링크를 정확한 `href`로 찾고 있어 프래그먼트가 붙자 실패했습니다. 전체 검색 결과는 접두사 비교로 바꿨고, 본문이 없는 빠른 검색 팔레트는 그대로 두었습니다.
