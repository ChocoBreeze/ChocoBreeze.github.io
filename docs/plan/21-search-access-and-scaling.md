# 21. 검색 접근성과 인덱스 확장성

## 현재 동작

- 검색은 제목·설명·태그·소제목·본문 요약에 가중치를 적용합니다.
- 본문 발췌와 검색 텍스트는 처음 5,000자 범위에서 분리 저장하고, 검색 시 두 필드를 논리적으로 연결해 경계 검색어를 보존합니다.
- 카테고리별 글 검색 인덱스와 별도 코드 검색을 제공합니다.
- 최근 빌드 기준 `search.json`은 약 3.73MiB, `code-search.json`은 약 2.35MiB입니다.
- 2026-09-27 재측정: 현재 JSON 인덱스 전체 10,604,428바이트, Pagefind 전체 8,407,258바이트, Pagefind 초기 전송량 118,350바이트입니다. Pagefind 초기화 55.5ms, 첫 결과 152.9ms였으며, 자세한 결과와 결정은 아래에 기록합니다.
- 전역 `Cmd/Ctrl+K` 검색 팔레트는 작은 `/search/quick.json`을 팔레트를 열 때만 요청합니다.
- 전체 검색 페이지는 처음 열 때 인덱스를 요청하지 않고, 두 글자 이상 검색할 때 선택한 인덱스를 지연 로드합니다.
- 이미 받은 전체·카테고리·코드 인덱스는 같은 페이지에서 다시 사용합니다.

## 목표

1. 어느 페이지에서든 검색을 빠르게 열 수 있게 합니다.
2. 사용하지 않는 대형 인덱스를 불필요하게 받지 않게 합니다.
3. 현재의 한국어 가중치 검색과 코드 검색을 보존하면서 확장 전략을 결정합니다.

## 권장 단계

### 1단계 — 측정과 빠른 접근

- [완료] 빌드마다 전체·카테고리·코드 인덱스 크기를 기록합니다.
- [완료] `Cmd/Ctrl+K` 팔레트에는 제목·카테고리·URL 중심의 소형 인덱스를 사용합니다.
- [완료] 팔레트를 열기 전에는 검색 인덱스를 내려받지 않습니다.

### 2단계 — 현재 검색 최적화

- [완료] 카테고리·코드 인덱스를 검색어 입력 이후에 지연 로드하고 경로별로 재사용합니다.
- [완료] 본문 검색 길이 5,000자는 유지하면서 발췌·검색 필드의 중복을 제거하고 경계 검색어 누락을 막았습니다.
- [완료] 코드 인덱스는 코드 검색 모드에서 두 글자 이상 입력할 때만 로드합니다.
- GitHub Pages 정적 배포는 Astro 런타임 `Response` 헤더를 보존하지 않으므로, 응답 헤더 기반 캐시 정책은 적용하지 않습니다.
- [완료] 배포 커밋 SHA를 검색 인덱스 요청의 `v` 쿼리로 사용해 변경된 인덱스가 새 URL로 요청되도록 합니다.

### 3단계 — 대안 벤치마크

Pagefind는 다음 항목을 같은 질의 세트로 비교한 뒤에만 채택합니다.

- 한국어 부분어·띄어쓰기·복합어 결과
- 제목·태그 가중치
- 코드 검색 보존 방법
- 초기 전송량과 첫 결과 시간
- 카테고리 필터와 결과 스니펫

벤치마크 도구는 `npm run build && npm run benchmark:search`로 실행합니다. Pagefind는
`.post-body`를 루트로 사용해 공개 글 503개만 색인하고, 기존 `search.json`, ETF
카테고리 인덱스, `code-search.json`을 같은 질의로 함께 측정합니다. Pagefind에는
`category:ETF` 필터 메타데이터를 부여해 ETF 인덱스와 동일한 범위를 별도로 검색합니다.
결과에는 각 엔진의 결과 수와 상위 결과, 상위 결과에 실제로 표시되는 스니펫, 기존
검색의 메모리 내 검색 시간, Pagefind의 초기 전송량·첫 결과 시간·질의별 검색 및
지연 결과 데이터 fetch를 포함한 전체 및 ETF 필터 검색 시간·전송량이 포함됩니다. 2026-09-27 실행에서는 현재
JSON 인덱스 전체가 10,604,428바이트, Pagefind 산출물 전체가 8,407,258바이트였고,
Pagefind 초기 전송량은 118,350바이트였습니다(엔트리·메타데이터·WASM 준비 포함). Pagefind 초기화는 55.5ms, 첫 결과는 152.9ms였습니다. `ETF`, `반도체`, `IAU`,
`git diff --cached`, 결과 없음 질의를 실행했으며, Pagefind는 한국어 stemming을
지원하지 않았습니다. 제목·태그 가중치와 별도 코드 검색의 결과가 서로 다르므로
**Pagefind 전면 교체는 보류**하고, 동일한 측정 절차로 재검토합니다.

2026-09-27 인덱스 크기: 전체 글 4,018,803바이트, 카테고리 인덱스 4,018,811바이트,
빠른 검색 99,367바이트, 코드 검색 2,467,447바이트(기존 JSON 인덱스 합계
10,604,428바이트), Pagefind 산출물 8,407,258바이트입니다. Pagefind 초기 전송량은
118,350바이트였습니다. 이번 실행의 질의별 결과·시간은 변동 폭이 있었으며, 1k·2k
합성 규모와 반복 측정 p50/p95는 실행하지 않았습니다. 따라서 이 측정은 현재 크기
비교만 갱신하며 Pagefind 채택 판단은 바꾸지 않습니다. 재검토 시 합성 규모 및 반복
측정을 보완합니다.

## 테스트 설계

- 한글·영문·티커·코드 구문 대표 질의의 기대 상위 결과 고정
- 발췌 경계를 넘는 긴 문구와 480자 이하 본문의 중복 검색 여부
- 1자·2자·공백·특수문자·결과 없음 입력
- 팔레트 열기 전 네트워크 요청이 발생하지 않는지 확인
- 포커스 트랩, Escape 닫기, 원래 요소로 포커스 복귀
- 카테고리 변경 중 요청 순서가 뒤바뀌는 경우
- 인덱스 로드 실패와 재시도 UI
- production 빌드에서 인덱스 크기 기록
- `npm run check`, `npm run build`, `npm run format:check`

## 완료 판단

- 검색 엔진 교체 자체를 완료 조건으로 삼지 않습니다.
- 현재 기능을 유지하면서 초기 전송량과 접근 단계가 줄어들면 목표를 달성한 것으로 봅니다.
