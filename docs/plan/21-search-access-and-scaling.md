# 21. 검색 접근성과 인덱스 확장성

## 현재 동작

- 검색은 제목·설명·태그·소제목·본문 요약에 가중치를 적용합니다.
- 본문 발췌와 검색 텍스트는 처음 5,000자 범위에서 분리 저장하고, 검색 시 두 필드를 논리적으로 연결해 경계 검색어를 보존합니다.
- 카테고리별 글 검색 인덱스와 별도 코드 검색을 제공합니다.
- 2026-09-27 빌드의 `search.json`은 3.82MiB(4,009,352바이트), `code-search.json`은 약 2.35MiB입니다.
- 2026-09-27 재측정: 현재 JSON 인덱스 전체 10,604,428바이트, Pagefind 전체 8,407,258바이트, Pagefind 초기 전송량 118,350바이트입니다. Pagefind 초기화 55.5ms, 첫 결과 152.9ms였으며, 자세한 결과와 결정은 아래에 기록합니다.
- 전역 `Cmd/Ctrl+K` 검색 팔레트는 작은 `/search/quick.json`을 팔레트를 열 때만 요청합니다.
- 전체 검색 페이지는 처음 열 때 인덱스를 요청하지 않고, 두 글자 이상 검색할 때 선택한 인덱스를 지연 로드합니다.
- 이미 받은 전체·카테고리·코드 인덱스는 같은 페이지에서 다시 사용합니다.

## 목표

1. 어느 페이지에서든 검색을 빠르게 열 수 있게 합니다.
2. 사용하지 않는 대형 인덱스를 불필요하게 받지 않게 합니다.
3. 현재의 한국어 가중치 검색과 코드 검색을 보존하면서 확장 전략을 결정합니다.

## 권장 단계

### 1단계 — 측정과 빠른 접근

- [완료] 빌드마다 전체·카테고리·코드 인덱스 크기를 기록합니다.
- [완료] `Cmd/Ctrl+K` 팔레트에는 제목·카테고리·URL 중심의 소형 인덱스를 사용합니다.
- [완료] 팔레트를 열기 전에는 검색 인덱스를 내려받지 않습니다.

### 2단계 — 현재 검색 최적화

- [완료] 카테고리·코드 인덱스를 검색어 입력 이후에 지연 로드하고 경로별로 재사용합니다.
- [완료] 본문 검색 길이 5,000자는 유지하면서 발췌·검색 필드의 중복을 제거하고 경계 검색어 누락을 막았습니다.
- [완료] 코드 인덱스는 코드 검색 모드에서 두 글자 이상 입력할 때만 로드합니다.
- GitHub Pages 정적 배포는 Astro 런타임 `Response` 헤더를 보존하지 않으므로, 응답 헤더 기반 캐시 정책은 적용하지 않습니다.
- [완료] 배포 커밋 SHA를 검색 인덱스 요청의 `v` 쿼리로 사용해 변경된 인덱스가 새 URL로 요청되도록 합니다.
- [완료] `npm run benchmark:search:scale`로 현재 글 수와 1k·2k 합성 인덱스의 JSON 크기, gzip 추정 크기, 파싱 시간, 검색 응답 p50/p95를 재현할 수 있습니다.
- [완료] 검색 점수 계산 때 정규화된 필드를 항목별로 재사용하고, 결과로 채택된 문서에서만 스니펫을 만듭니다. 캐시는 원본 필드 스냅샷을 검사해 항목이 수정되면 갱신합니다.

### 3단계 — 대안 벤치마크

Pagefind는 다음 항목을 같은 질의 세트로 비교한 뒤에만 채택합니다.

- 한국어 부분어·띄어쓰기·복합어 결과
- 제목·태그 가중치
- 코드 검색 보존 방법
- 초기 전송량과 첫 결과 시간
- 카테고리 필터와 결과 스니펫

벤치마크 도구는 `npm run build && npm run benchmark:search`로 실행합니다. Pagefind는
`.post-body`를 루트로 사용해 공개 글 503개만 색인하고, 기존 `search.json`, ETF
카테고리 인덱스, `code-search.json`을 같은 질의로 함께 측정합니다. Pagefind에는
`category:ETF` 필터 메타데이터를 부여해 ETF 인덱스와 동일한 범위를 별도로 검색합니다.
결과에는 각 엔진의 결과 수와 상위 결과, 상위 결과에 실제로 표시되는 스니펫, 기존
검색의 메모리 내 검색 시간, Pagefind의 초기 전송량·첫 결과 시간·질의별 검색 및
지연 결과 데이터 fetch를 포함한 전체 및 ETF 필터 검색 시간·전송량이 포함됩니다. 2026-09-27 실행에서는 현재
JSON 인덱스 전체가 10,604,428바이트, Pagefind 산출물 전체가 8,407,258바이트였고,
Pagefind 초기 전송량은 118,350바이트였습니다(엔트리·메타데이터·WASM 준비 포함). Pagefind 초기화는 55.5ms, 첫 결과는 152.9ms였습니다. `ETF`, `반도체`, `IAU`,
`git diff --cached`, 결과 없음 질의를 실행했으며, Pagefind는 한국어 stemming을
지원하지 않았습니다. 제목·태그 가중치와 별도 코드 검색의 결과가 서로 다르므로
**Pagefind 전면 교체는 보류**하고, 동일한 측정 절차로 재검토합니다.

2026-10-07에는 `npm run benchmark:search:pagefind-scale -- 1000,2000`으로 합성 1k·2k
Pagefind 비교를 추가했습니다. 원본 본문·필터를 보존하면서 각 HTML에 질의와 무관한 고유
표식을 추가해 Pagefind가 같은 본문의 문서들을 중복으로 합치지 않게 했습니다. 1k에서
Pagefind 출력은 7,715,626바이트, 초기 전송 추정 118.56KiB, 초기화 58.7ms였고, 2k에서는
11,892,245바이트, 125.06KiB, 66.4ms였습니다. 2k `반도체`는 Pagefind 질의와 상위 3개 결과
상세 fetch를 합쳐 449.1ms, resident JSON 검색은 160.9ms였고 ETF 질의는 각각 101.3ms와
258.3ms였습니다. JSON 인덱스는 이미 메모리에 있으므로 이 시간은 직접 속도 비교가 아닙니다.
질의별 결과 수와
전송량은 [합성 Pagefind 측정 기록](search-pagefind-scale-benchmark-2026-10-07.md)에
보존했습니다. 반복된 원문으로 만든 corpus라 향후 글의 검색 품질 분포를 대표하지 않으며,
각 Pagefind 시간도 단일 실행 값입니다.

같은 날 `npm run benchmark:search:browser -- 506,1000,2000 30`으로 Chromium 입력→결과 DOM
변경 지연과 JS heap을 측정했습니다. 현재 506개 corpus의 cold ETF 검색은 147.80ms였고,
warm p95는 ETF 33.80ms·반도체 46.60ms였습니다. 2k 합성 corpus에서는 cold ETF 752.20ms,
warm p95 ETF 298.40ms·반도체 386.10ms였습니다. warm 표본은 결과 DOM을 비우지 않고 두 질의를
연속 교체해 앱의 인덱스 캐시를 유지한 값입니다. 강제 GC 후 CDP heap의 인덱스 상주 증가분은
506개 14.16MiB, 2k 54.69MiB였고, 2k ETF 결과 DOM은 11,462개 노드였습니다. 1k·2k 수치는
검색 레코드를 round-robin 복제한 규모 실험입니다. 브라우저별 전체 값과 측정 경계는
[브라우저 측정 기록](search-browser-benchmark-2026-10-07.md)에 있습니다. 506개 현재
corpus에서는 이 실험으로 결과 렌더링 제한을 도입할 병목을 확인하지 못했고, 사용자 실제
환경의 압축 전송·성능은 별도 미측정입니다.

2026-09-27 검색 규모 결과는 `npm run benchmark:search:scale -- dist/search.json 30`
출력 기준입니다. Node v24.19.0, Windows x64, Intel i7-1360P에서 2회 warm-up 후
30회 측정했습니다. 503개 실제 글 인덱스 4,009,352바이트, gzip(level 9) 추정
1,173,639바이트, JSON parse p50/p95 7.67/10.18ms, 첫 검색(cold) 71.16ms였습니다.
같은 콘텐츠를 round-robin으로 복제한 1,000개는 8,002,499바이트·gzip 추정
2,340,211바이트·parse 14.49/18.59ms·cold 119.92ms였고, 2,000개는 16,015,572바이트·
4,681,991바이트·parse 29.75/34.72ms·cold 252.68ms였습니다.

30회 반복에서 검색 p50/p95(ms)는 503개 기준 ETF 21.89/27.23, 반도체 42.13/47.33,
IAU 6.89/10.90, `git diff --cached` 1.22/1.54, 결과 없음 0.87/0.99였습니다.
1,000개는 각각 45.21/51.87, 87.89/92.45, 12.26/13.54, 2.40/3.22, 1.70/1.84였고,
2,000개는 90.51/102.03, 179.87/190.38, 25.87/30.63, 5.56/6.90, 3.85/4.08였습니다.

반복 검색 개선 전 503개 인덱스의 대표 query p50은 ETF 148.64ms, 반도체 208.03ms,
IAU 248.96ms, 코드 문구 248.38ms, 결과 없음 248.90ms였습니다. 검색 필드 정규화
캐시와 일치 결과만 스니펫을 만드는 변경 후 같은 Node 환경에서 10회 측정한 p50은 각각
22.41ms, 42.71ms, 6.25ms, 1.65ms, 1.01ms였습니다. 결과 순위와 스니펫 회귀 테스트는
유지했습니다. 비교 표본은 10회이므로 이 전후 값은 개선 규모를 가늠하는 참고치이며,
튜닝 판단에는 위의 30회 결과를 사용합니다. 2,000개에서 결과가 많이 일치하는 한국어
query는 p50 179.87ms, p95 190.38ms로 100ms를 넘으므로, 글 수와 결과 표시량이 더 커질 때
브라우저 기준 계측을 보완해야 합니다.

JSON 규모 도구는 대표 글 텍스트·카테고리 분포를 유지한 인덱스를 측정합니다. 별도
Pagefind 스크립트는 HTML 합성 corpus를 만들고, 브라우저 스크립트는 로컬 loopback에서
Chromium을 구동합니다. 브라우저 입력→DOM과 JS heap은 2026-10-07에 30회 표본으로
측정했으며 nearest-rank p50/p95입니다. 실제 GitHub Pages/CDN의 압축 전송량, 사용자
기기·네트워크 분포, 스로틀링 환경은 여전히 측정하지 않았습니다. 모든 benchmark는 CI
성능 문턱값으로 사용하지 않습니다.

별도의 2026-09-27 Pagefind 비교 실행에서는 당시 글 집합 기준 Pagefind 산출물
8,407,258바이트, 초기 전송 118,350바이트, 초기화 55.5ms, 첫 결과 152.9ms였습니다.
당시 JSON 합계는 10,604,428바이트였습니다. 이 기록은 현재 콘텐츠 집합의 Pagefind
크기 비교이며, synthetic 1k·2k 결과는 위의 2026-10-07 기록을 참조합니다.
본문 점수·한국어 부분 검색·별도 코드 검색 품질이 달라 전면 전환 보류 판단은 유지합니다.

## 테스트 설계

- 한글·영문·티커·코드 구문 대표 질의의 기대 상위 결과 고정
- 발췌 경계를 넘는 긴 문구와 480자 이하 본문의 중복 검색 여부
- 1자·2자·공백·특수문자·결과 없음 입력
- 팔레트 열기 전 네트워크 요청이 발생하지 않는지 확인
- 포커스 트랩, Escape 닫기, 원래 요소로 포커스 복귀
- 카테고리 변경 중 요청 순서가 뒤바뀌는 경우
- 인덱스 로드 실패와 재시도 UI
- production 빌드에서 인덱스 크기 기록
- `npm run check`, `npm run build`, `npm run format:check`

## 완료 판단

- 검색 엔진 교체 자체를 완료 조건으로 삼지 않습니다.
- 현재 기능을 유지하면서 초기 전송량과 접근 단계가 줄어들면 목표를 달성한 것으로 봅니다.
