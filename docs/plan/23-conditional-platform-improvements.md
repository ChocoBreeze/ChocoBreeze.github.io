# 23. 조건부 플랫폼 개선

이 문서는 즉시 구현 목록이 아니라 명확한 착수 조건이 필요한 후보를 관리합니다. 각 항목은 착수 시 별도 번호의 계획 문서로 분리합니다.

## 방문 통계와 통계 페이지

### 목적

- 카테고리·시리즈별 관심도와 유입 경로를 파악합니다.
- 공개 가능한 집계 데이터를 `/stats`의 연도·월별 글 수, 카테고리 분포와 결합할 수 있습니다.

### 착수 조건

- 수집할 지표와 보존 기간이 정해져야 합니다.
- 쿠키·개인정보·외부 전송 범위를 비교해야 합니다.
- Plausible·Umami·GA4 중 이름만으로 선택하지 않고 GitHub Pages 환경의 비용과 정책을 확인해야 합니다.

방문 통계는 12~15번의 명백한 사용성 개선보다 먼저 필요한 선행 조건이 아닙니다.

## Mermaid 다이어그램

### 착수 조건

- 실제 적용할 Git Internals 또는 반도체 글을 먼저 선정합니다.
- 정적 SVG 생성과 클라이언트 렌더링의 빌드 비용·보안·접근성을 비교합니다.
- 다이어그램마다 텍스트 대체 설명을 제공할 수 있어야 합니다.

## 뉴스레터

### 착수 조건

- Market Brief의 발행 주기와 구독 수요를 확인합니다.
- Buttondown 등 외부 서비스의 개인정보 처리와 무료 범위를 확인합니다.
- RSS와 중복되는 가치, 구독 해지, 발송 실패 처리 방식을 정합니다.

## 폰트·KaTeX 셀프 호스팅

### 현재 사실

- 사이트는 Google Fonts의 Inter·Noto Sans KR과 jsDelivr의 KaTeX CSS를 사용합니다.
- `public/fonts/`에는 Atkinson 폰트만 있어 기존 파일을 옮기는 것만으로 대체할 수 없습니다.

### 착수 조건

- 실제 네트워크 워터폴과 렌더 블로킹 시간을 측정합니다.
- 사용할 글꼴 굵기와 한글 서브셋, 라이선스를 확인합니다.
- KaTeX CSS와 연관 폰트 자산을 함께 관리할 수 있어야 합니다.

## 접근성·성능 자동 검사

- UI 변경이 누적된 뒤 핵심 경로의 Lighthouse 또는 axe 기준선을 정합니다.
- 점수 자체보다 키보드 접근, 명도 대비, JS·CSS·검색 인덱스 크기 예산을 관리합니다.
- 자동화 도구 추가가 CI 시간을 과도하게 늘리지 않는지 확인합니다.

## 명시적 범위 제외

- giscus를 포함한 댓글 기능
- 브라우저 localStorage 기반 북마크·최근 본 글·읽은 글 표시
- Git 커밋 시각을 `updatedDate` 또는 `verifiedDate`로 자동 주입하는 기능

## 공통 검증

각 후보가 실제 계획으로 승격될 때 다음을 문서화합니다.

1. 수집하거나 외부로 전송되는 데이터
2. 운영 비용과 서비스 종속성
3. 실패 시 사이트 핵심 기능의 폴백
4. 번들·빌드·네트워크 비용 기준선과 변경 후 수치
5. 철회하거나 교체할 때의 데이터·코드 제거 방법
