## 핵심 요약

- 웹의 주요 차이는 작업이 내 PC가 아닌 클라우드 환경에서 실행된다는 점입니다.
- 명확하게 나눌 수 있는 작업을 맡기고 브랜치·PR로 검토하기에 적합합니다.
- 로컬 장비나 사내 서비스가 필요한 작업은 실행 위치와 네트워크 연결을 먼저 확인해야 합니다.

## 브라우저에서 쓴다고 모두 클라우드는 아니다

Claude Code를 비교할 때는 화면보다 **코드와 도구가 실행되는 위치**가 중요합니다. 클라우드 세션은 원격 환경에서 실행되지만, Remote Control은 로컬 세션에 다른 기기에서 접속하는 방식입니다.[1]

따라서 휴대폰에서 대화하고 있다는 사실만으로 로컬 PC를 꺼도 된다고 결론 내릴 수는 없습니다.

| 구분 | 클라우드 세션 | 로컬 세션 | 로컬 세션의 Remote Control |
| --- | --- | --- | --- |
| 실행 위치 | 원격 환경 | 내 PC·서버 | 원래 로컬 환경 |
| 로컬에만 있는 설정 | 자동으로 가져오지 않음 | 사용 가능 | 로컬 세션의 설정 사용 |
| 내 PC를 껐을 때 | 클라우드 작업은 계속될 수 있음 | 실행 중단 | 실행 중단 |
| 로컬 장비·DB 접근 | 원격 환경의 연결 필요 | 로컬 연결 활용 | 원래 로컬 연결 활용 |

클라우드 실행도 무한히 계속되는 것은 아닙니다. 세션·환경의 제한과 사용량 정책이 있으므로, 장시간 작업은 해당 환경의 조건을 확인해야 합니다.[2]

## 클라우드가 편한 작업

공식 시작 안내는 독립 작업의 병렬 실행, 로컬에 없는 저장소 탐색, 자주 개입하지 않아도 되는 명확한 작업을 활용 사례로 듭니다.[3]

블로그 저장소라면 “정해진 글감 5개를 기존 형식으로 작성하고 링크 검사를 실행하라”처럼 결과와 검증 조건이 분명한 요청이 잘 맞습니다. 작업별 브랜치를 나눠 변경을 비교하기도 편합니다.

다만 실행 환경이 나뉘었다고 변경 내용까지 충돌하지 않는 것은 아닙니다. 두 세션이 같은 메뉴 파일을 수정하면 PR 병합 시 충돌하거나, 함께 적용한 결과가 어긋날 수 있습니다. 작업을 파일·기능 단위로 나누고 최종 결합 결과를 검토해야 합니다.

## 로컬이 필요한 작업

다음 조건에서는 로컬 환경을 활용하는 편이 단순할 수 있습니다.

- 실제 장비나 시뮬레이터에 연결해야 하는 경우
- 사내 DB·Maven 저장소처럼 특정 네트워크에서만 접근 가능한 의존성이 있는 경우
- 아직 공유하지 않은 로컬 코드·설정·실행 상태가 중요한 경우
- 코드 탐색과 실험을 짧은 주기로 함께 진행하는 경우

이것은 클라우드가 이런 작업을 원리적으로 할 수 없다는 뜻은 아닙니다. 원격 환경에 필요한 연결과 도구를 준비할 수 있는지에 따른 선택입니다. 현재 공식 문서에는 조직의 self-hosted 환경도 구분되어 있습니다.[1][2]

## 네트워크와 설정은 별도로 준비한다

Anthropic 호스팅 클라우드는 환경별로 네트워크 수준과 초기 설정을 관리합니다.[2] “웹은 패키지 저장소만 접근한다”처럼 고정된 범위로 외우기보다 선택한 환경의 정책을 확인해야 합니다.

프로젝트 파일이 있어도 실행에 필요한 모든 것이 준비됐다는 뜻은 아닙니다. 의존성 설치, 환경 변수, 서비스 시작과 테스트 명령을 정리해 두면 새 환경에서도 작업을 재현하기 쉽습니다.

실행 환경이 격리되어 있다는 점도 저장소나 외부 서비스에 대한 쓰기 권한을 없애지는 않습니다. 연결한 GitHub 권한은 [저장소 접근 범위 설정](/blog/programming/claude-code-github-repository-access)에서 따로 확인해야 합니다.

## GitHub가 반드시 필요한가?

브라우저의 일반적인 시작 흐름은 GitHub 저장소 연결을 사용합니다.[3] 하지만 현재 공식 클라우드 문서는 CLI에서 로컬 저장소를 번들로 보내는 경로도 설명합니다.[1] 따라서 “GitHub 이외의 코드는 어떤 방법으로도 사용할 수 없다”는 설명은 현재 기준으로 너무 넓습니다.

번들 업로드와 GitHub 원격 저장소 연동은 같은 기능이 아닙니다. 업로드 대상 파일과 이력의 범위, 결과를 가져오는 방법을 확인해야 합니다. 조직의 소스 반출 정책도 실행 방식과 함께 검토해야 합니다.

## 결과는 변경과 검증 근거로 검토한다

클라우드에서는 브랜치의 diff를 확인하고 PR로 이어갈 수 있습니다.[3] PR 생성 자체가 품질 검증을 의미하지는 않으므로, 다음 항목이 명확하면 좋습니다.

1. 바꾸려던 문제가 무엇인지
2. 실제로 수정한 파일과 동작이 무엇인지
3. 실행한 검사와 결과가 무엇인지
4. 검증하지 못한 항목이 무엇인지

로컬이나 클라우드 어느 쪽이든 이 기준은 같습니다. 개인 블로그처럼 외부 저장소에서 독립적으로 재현 가능한 작업은 클라우드로 맡기고, 장비 연결이 필요한 작업은 로컬에서 진행하는 식으로 나누면 선택 기준이 분명해집니다.
