## 핵심 요약

- 인덱스는 키를 이용한 행 접근을, 파티션 프루닝은 불필요한 파티션 제외를 돕습니다. 두 최적화는 함께 적용될 수 있습니다.
- `type = ALL`이 유지돼도 검색할 파티션이 줄어들 수 있습니다.
- `rows`는 추정치입니다. 파티션 수와 추정 행 수 감소를 실제 실행 시간 개선과 구분해야 합니다.

## 날짜 조건을 바꿨는데 ALL이 그대로라면

날짜 컬럼에 적용한 `DATE()`를 제거한 뒤 `EXPLAIN`을 비교한다고 가정하겠습니다. 변경 전후 모두 `type = ALL`인데 `partitions`와 `rows`는 줄었다면 어떻게 설명해야 할까요?

“인덱스를 탔으니 빨라졌다”라고 쓰기 전에, **행에 접근하는 방식과 접근할 파티션의 범위를 따로 봐야 합니다.** 이 글은 MySQL 8.4의 실행 계획을 기준으로 설명합니다.

## 인덱스와 파티션은 줄이는 단위가 다르다

B-tree 인덱스는 정렬된 키 구조를 이용해 원하는 값이나 범위에 접근할 수 있게 합니다. 일반적인 인덱스 키와 상수 사이의 비교는 범위 검색의 후보가 됩니다.[1]

반면 파티셔닝은 하나의 논리적 테이블을 정해진 기준으로 나누는 기능입니다. Partition Pruning은 쿼리 조건과 파티션 정의를 바탕으로, 결과에 기여하지 않는 파티션을 검색 대상에서 제외하는 최적화입니다.[2]

| 구분 | 인덱스 접근 | 파티션 프루닝 |
| --- | --- | --- |
| 줄이는 범위 | 인덱스 키를 통한 행 접근 범위 | 조회할 파티션 |
| 필요한 조건 | 적절한 인덱스와 검색 조건, 비용 판단 | 파티션 정의와 해석 가능한 검색 조건 |
| 실행 계획에서 볼 곳 | `type`, `key`, `possible_keys` 등 | `partitions` |
| 함께 적용 | 남은 파티션에서 인덱스 사용 가능 | 인덱스 없이 일부 파티션 스캔도 가능 |

인덱스가 있어도 넓은 범위를 읽는 쿼리라면 옵티마이저가 전체 스캔을 더 유리하게 판단할 수 있습니다. 인덱스 존재와 실제 선택은 같은 말이 아닙니다.

## 날짜 컬럼의 함수 제거

다음은 MyBatis 파라미터를 사용한 조건의 예입니다. `MODIFY_TIME`은 유효한 `DATETIME` 값이며, `FROM_DATE`는 날짜 문자열이라는 전제입니다.

```sql
-- 변경 전
AND DATE(AH.MODIFY_TIME) >= DATE(DATE_FORMAT(#{FROM_DATE}, '%Y-%m-%d'))

-- 변경 후
AND AH.MODIFY_TIME >= DATE(DATE_FORMAT(#{FROM_DATE}, '%Y-%m-%d'))
```

오른쪽은 기준 날짜의 0시로 비교되고, 왼쪽 컬럼은 원래 값 그대로 비교할 수 있게 됩니다. 날짜 경계를 애플리케이션에서 만들어 타입에 맞게 바인딩하면 오른쪽 표현식도 단순화할 수 있습니다.

다만 데이터 타입, 잘못된 날짜 값의 처리, 입력 형식, `TIMESTAMP`의 세션 시간대 등에 따라 의미를 다시 확인해야 합니다. 날짜만 출력하는 SELECT 표현식과 검색 범위를 정하는 WHERE 조건도 구분하는 것이 좋습니다.

컬럼에 함수를 씌우면 일반 컬럼 인덱스의 범위 조건으로 직접 활용하기 어려워질 수 있습니다. 하지만 함수 기반 인덱스나 생성 컬럼 등 예외가 있으므로 “함수가 있으면 어떤 인덱스도 절대 못 쓴다”라고 일반화해서는 안 됩니다.

프루닝 역시 모든 함수에 똑같이 반응하지 않습니다. MySQL이 이해하는 파티션 표현식과 조건의 조합이 있으므로 실제 정의와 계획을 확인해야 합니다.[2]

## 작은 테이블로 확인할 수 있는 예제

다음은 **개념 확인용 DDL이며 실측 성능 결과는 아닙니다.** 새 테스트 DB에서 실행할 예제로, 기본 키에 파티션 컬럼도 포함했습니다.

```sql
CREATE TABLE action_history_demo (
    id BIGINT NOT NULL,
    modify_time DATETIME NOT NULL,
    payload VARCHAR(100),
    PRIMARY KEY (id, modify_time),
    KEY idx_modify_time (modify_time)
) ENGINE = InnoDB
PARTITION BY RANGE COLUMNS (modify_time) (
    PARTITION p_before VALUES LESS THAN ('2026-10-01'),
    PARTITION p202610 VALUES LESS THAN ('2026-11-01'),
    PARTITION p_future VALUES LESS THAN (MAXVALUE)
);

INSERT INTO action_history_demo VALUES
    (1, '2026-09-30 23:59:59', 'September'),
    (2, '2026-10-19 12:00:00', 'October'),
    (3, '2026-11-01 00:00:00', 'November');

EXPLAIN FORMAT=TRADITIONAL
SELECT * FROM action_history_demo
WHERE modify_time >= '2026-10-01'
  AND modify_time < '2026-11-01';
```

이 정의에서는 10월 범위가 `p202610`에 들어가므로, 해당 파티션으로 검색 범위가 좁혀지는지 확인할 수 있습니다.

MySQL 8.4는 설정에 따라 `EXPLAIN`의 기본 출력 형식이 달라질 수 있으므로, 여기서는 `FORMAT=TRADITIONAL`을 명시해 표 형태의 컬럼을 확인합니다.[4]

데이터가 적으면 `type`이 반드시 `range`가 되지는 않습니다. `type`, `key`, `partitions`를 함께 확인합니다. 또한 상한 없이 `modify_time >= '2026-10-01'`만 지정하면 11월 이후를 담는 `p_future`도 결과의 후보입니다.

## EXPLAIN에서 무엇을 확인할까?

| 항목 | 의미와 주의점 |
| --- | --- |
| `partitions` | 접근 대상으로 남은 파티션 |
| `type` | `ALL`, `range` 등 테이블 접근 방식 |
| `possible_keys` | 접근에 사용할 수 있는 후보. 실제 선택과는 다름 |
| `key` | 선택한 인덱스 |
| `rows` | 옵티마이저가 검사할 것으로 추정한 행 수 |

`ALL`은 테이블 스캔을 나타내지만, 파티션 테이블에서는 대상으로 남은 파티션 범위도 함께 읽어야 합니다. InnoDB의 `rows`는 실제로 읽은 행 수가 아닌 추정치입니다.[3]

변경 후에도 `type = ALL`이고 `partitions`가 줄었다면, 우선 “검색 대상 파티션을 줄였다”라고 설명할 수 있습니다. 인덱스 범위 검색으로 전환된 것까지 확인하지 않았다면 두 성과를 섞지 않는 것이 중요합니다.

## 리뷰와 보고에는 어떻게 쓸까?

예를 들어 다음처럼 확인한 범위를 명시할 수 있습니다.

> 날짜 컬럼의 함수 적용을 제거하여 실행 계획상 접근 대상 파티션과 예상 검사 행 수의 감소를 확인했다. 접근 방식은 ALL을 유지하며, 실행 시간 개선은 별도로 측정한다.

실행 시간을 평가하려면 같은 파라미터와 같은 데이터로 결과의 동등성을 확인하고, 캐시와 동시 부하 조건도 맞춰야 합니다. `EXPLAIN ANALYZE`는 쿼리를 실제로 실행하므로, 먼저 관리 가능한 검증 환경에서 다룹니다.[4]

파티션을 줄인 것은 실행 계획의 개선으로 보고할 수 있지만, 그것만으로 몇 배 빨라졌다고 말할 수는 없습니다. 관측한 계획과 측정한 시간을 분리하면 개선 내용을 정확하게 전달할 수 있습니다.
