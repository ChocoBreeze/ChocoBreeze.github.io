## 핵심 요약

- TOCTOU는 상태를 확인한 시점과 실제 사용 시점 사이에 상태가 바뀌어 생기는 경쟁 조건입니다.
- 확인과 변경을 같은 보호 범위 안에서 수행해야 합니다. 개별 메서드의 스레드 안전성만으로 충분하지 않을 수 있습니다.
- Java 객체의 락은 같은 JVM 안에서 공유하는 객체를 보호합니다. 여러 서버가 공유하는 DB 상태에는 DB 차원의 제어가 필요합니다.

## 확인했는데 왜 실패할까?

TOCTOU는 Time Of Check To Time Of Use의 약자입니다. MITRE CWE-367은 확인한 자원의 상태가 사용 전에 변경될 수 있는 문제를 설명합니다.[1]

계좌의 잔액을 확인한 뒤 출금하는 다음 코드를 생각해 보겠습니다. 출금 메서드 안에서 잔액을 다시 검사하지 않고 차감한다고 가정한 개념 예제입니다.

```java
if (account.getBalance() >= 1000) {
    account.withdrawUnchecked(1000);
}
```

초기 잔액이 1,000원이고, 두 스레드가 아래 순서로 실행되면 문제가 생깁니다.

| 순서 | 스레드 A | 스레드 B | 잔액 |
| --- | --- | --- | --- |
| 1 | 잔액 1,000원 확인 | 대기 | 1,000원 |
| 2 | 대기 | 잔액 1,000원 확인 | 1,000원 |
| 3 | 1,000원 차감 | 대기 | 0원 |
| 4 | 대기 | 이전 확인을 믿고 1,000원 차감 | -1,000원 |

두 차감 자체는 순서대로 일어나더라도, 확인과 차감의 조합은 안전하지 않을 수 있습니다. `getBalance()`와 `withdrawUnchecked()`에 각각 `synchronized`를 붙여도 두 호출 사이의 틈은 남습니다.

## 확인과 변경을 하나의 연산으로 만들기

다음은 `ToctouDemo.java` 전체 예제입니다. 같은 계좌 객체에 두 스레드가 출금을 시도해도 한 번만 성공하도록 만듭니다. 금액은 원 단위 정수라고 가정합니다.

```java
import java.util.concurrent.atomic.AtomicInteger;

public class ToctouDemo {
    static class Account {
        private long balance = 1000;

        synchronized boolean withdraw(long amount) {
            if (amount <= 0) {
                throw new IllegalArgumentException("amount must be positive");
            }
            if (balance < amount) {
                return false;
            }
            balance -= amount;
            return true;
        }

        synchronized long getBalance() {
            return balance;
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Account account = new Account();
        AtomicInteger successes = new AtomicInteger();
        Runnable task = () -> {
            if (account.withdraw(1000)) {
                successes.incrementAndGet();
            }
        };
        Thread first = new Thread(task);
        Thread second = new Thread(task);
        first.start();
        second.start();
        first.join();
        second.join();

        System.out.println("successes: " + successes.get());
        System.out.println("balance: " + account.getBalance());
    }
}
```

출력은 다음과 같습니다. 어느 스레드가 먼저 성공하는지는 정하지 않습니다.

```text
successes: 1
balance: 0
```

인스턴스의 `synchronized` 메서드는 해당 객체의 모니터 락을 사용합니다.[2] 여기서는 잔액 확인부터 차감까지 같은 락 안에 있으므로 다른 출금이 그 사이에 끼어들지 못합니다.

이 예제가 잘못된 코드의 경쟁 상황을 반드시 재현하는 테스트는 아닙니다. 안전한 연산의 경계와 결과를 보여주는 예제입니다. 같은 잔액을 변경하는 다른 경로가 생긴다면 그 경로도 같은 동기화 정책을 따라야 합니다.

## 서버가 두 대면 synchronized만으로 충분할까?

서버 A와 B가 각각 메모리에 만든 계좌 객체는 서로 다른 락을 사용합니다. 같은 JVM에서도 별도의 객체 두 개를 만들면 락을 공유하지 않습니다.

실제 잔액이 DB에 있다면 조건 확인과 변경을 DB에서 함께 수행하는 방법을 고려할 수 있습니다. 다음은 MySQL InnoDB에서, 기본 키 `id`가 42인 계좌에 대해 실행할 조건부 UPDATE 예제입니다.

```sql
UPDATE accounts
SET balance = balance - 1000
WHERE id = 42
  AND balance >= 1000;
```

영향받은 행이 1개면 해당 변경이 수행된 것이고, 0개면 계좌 부재 또는 잔액 조건 불충족 등을 구분해 처리해야 합니다. InnoDB의 UPDATE는 대상 레코드에 잠금을 사용합니다.[3] 실행 결과와 트랜잭션 커밋까지 성공했는지 함께 확인해야 합니다.

다른 선택으로는 같은 트랜잭션에서 `SELECT ... FOR UPDATE` 후 검사·변경하기, 버전 컬럼을 이용한 낙관적 잠금 등이 있습니다. 여러 계좌를 함께 바꾸는 업무라면 트랜잭션 범위와 교착 상태 재시도도 설계해야 합니다.

단순히 `@Transactional`을 붙였다는 사실만으로 모든 확인 후 변경이 직렬화되는 것은 아닙니다. 격리 수준, 조회 방식, 잠금과 갱신 조건을 함께 봐야 합니다.

## 다른 곳에서도 같은 형태가 나타난다

| 상황 | 확인과 사용 사이에 생길 수 있는 변화 |
| --- | --- |
| 재고 확인 후 주문 | 다른 주문이 재고를 먼저 소진 |
| 파일 존재 확인 후 열기 | 파일 삭제·교체 또는 경로 변경 |
| 중복 데이터 조회 후 INSERT | 다른 요청이 같은 값을 먼저 저장 |

파일은 지원되는 원자적 파일 API와 경로 정책을, 중복 저장은 DB의 유일성 제약과 오류 처리를 검토하는 식으로 자원에 맞는 보호 수단을 선택합니다. TOCTOU는 경쟁 조건의 한 종류이며, 모든 경쟁 조건이 확인 후 사용의 형태인 것은 아닙니다.
