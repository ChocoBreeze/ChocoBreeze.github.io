## 핵심 요약

- 둘 다 코드로 브라우저를 조작하는 도구이며, 테스트와 화면 자동화 등에 사용할 수 있습니다.
- Playwright는 Java를 공식 지원하며, Chromium·Firefox·WebKit에서 동작을 확인할 수 있습니다.
- Puppeteer도 Firefox와 Locator 자동 대기를 지원합니다. 오래된 비교표의 “Chrome 전용”, “자동 대기 없음”을 그대로 적용하면 부정확합니다.

## 무엇을 자동화하는 도구일까?

브라우저 자동화는 페이지를 열고, 입력하고, 버튼을 누르고, 결과를 확인하는 일을 코드로 표현하는 것입니다. Playwright와 Puppeteer는 이런 작업에 필요한 API를 제공합니다.

백엔드 단위 테스트가 개별 메서드의 결과를 확인한다면, 브라우저 테스트는 사용자가 보는 화면을 통해 동작을 확인할 수 있습니다. 실제 서버에 접속하면 화면과 API가 연결되는 흐름도 검사할 수 있습니다. 반대로 페이지를 코드 안에서 만들어 실행하면 UI 동작만 작게 실험할 수 있습니다.

## 주요 차이

아래는 2026년 10월 16일 공식 문서 기준의 비교입니다.[1][2][3]

| 항목 | Puppeteer | Playwright |
| --- | --- | --- |
| 주요 사용 언어 | JavaScript·TypeScript | JavaScript·TypeScript, Java, Python, .NET |
| 지원 브라우저 | Chrome·Firefox | Chromium·Firefox·WebKit |
| 자동 대기 | Locator API에서 지원 | Locator 동작과 재시도 단언 지원 |
| 테스트 구성 | 별도의 테스트 러너와 조합 | JS·TS용 Playwright Test 제공, Java는 JUnit·TestNG 등과 조합 |
| 활용 | 브라우저 자동화, 수집, 화면·PDF 생성 등 | 브라우저 자동화, 여러 엔진의 E2E 테스트 등 |

WebKit 지원은 Safari와 같은 엔진 계열을 시험할 수 있다는 의미입니다. 사용자의 모든 Safari 버전이나 실제 기기를 그대로 재현한다는 뜻은 아닙니다.

또한 Playwright Test의 기능과 Java 라이브러리의 기능을 구분해야 합니다. `@playwright/test`를 설치하는 Node.js 예제를 Java 프로젝트에 그대로 적용하지는 않습니다. Java에서는 JUnit·TestNG 등으로 테스트 실행과 생명주기를 구성합니다.[4]

## 자동 대기는 무엇을 기다릴까?

화면이 준비되기 전에 클릭하면 테스트가 간헐적으로 실패할 수 있습니다. Playwright는 클릭 전에 대상이 보이고, 안정된 위치에 있으며, 이벤트를 받을 수 있고, 활성화되어 있는지 등을 확인합니다. 단언도 조건이 충족될 때까지 정해진 시간 안에서 재시도합니다.[5]

Puppeteer의 Locator 역시 요소가 준비된 상태가 되기를 기다립니다.[3] 따라서 “Puppeteer는 항상 직접 기다려야 한다”는 비교는 현재 API를 충분히 반영하지 못합니다.

어느 쪽이든 자동 대기가 모든 업무 상태를 알아서 판단하지는 않습니다. 주문 생성 후 처리 상태가 바뀌는 기능이라면, 버튼을 클릭할 수 있는지와 별도로 결과 상태를 단언해야 합니다.

## Playwright Java로 작은 동작 확인하기

다음 예제는 로그인 서버나 계정 없이 실행할 수 있도록 HTML을 직접 만듭니다. 버튼 클릭 후 안내 문구가 바뀌는지만 검사합니다. Playwright Java 의존성과 해당 버전에 맞는 Chromium 설치가 전제입니다.

```java
import com.microsoft.playwright.Browser;
import com.microsoft.playwright.Page;
import com.microsoft.playwright.Playwright;
import com.microsoft.playwright.options.AriaRole;
import java.nio.file.Paths;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

public class BrowserSmoke {
    public static void main(String[] args) {
        try (Playwright playwright = Playwright.create()) {
            Browser browser = playwright.chromium().launch();
            try {
                Page page = browser.newPage();
                page.setContent(
                    "<button onclick=\"document.getElementById('result').textContent='저장 완료'\">"
                    + "저장</button><p id='result' role='status'>대기 중</p>"
                );

                page.getByRole(AriaRole.BUTTON,
                    new Page.GetByRoleOptions().setName("저장")).click();
                assertThat(page.getByRole(AriaRole.STATUS)).hasText("저장 완료");
                page.screenshot(new Page.ScreenshotOptions()
                    .setPath(Paths.get("result.png")));
            } finally {
                browser.close();
            }
        }
    }
}
```

`getByRole()`은 역할과 접근성 이름으로 대상을 찾습니다. 화면에서 “저장”으로 표시되는 버튼을 표현하므로, 위치에 의존하는 좌표 클릭보다 의도를 읽기 쉽습니다. CSS 선택자가 쓸모없다는 뜻은 아니며, 화면에 맞는 안정적인 식별자를 선택하면 됩니다.

Maven 프로젝트에서는 `com.microsoft.playwright:playwright` 의존성에 사용할 버전을 명시해야 합니다. 버전 값은 공식 설치 문서에서 확인하고 프로젝트에서 고정하세요.[1] 브라우저 설치는 해당 의존성이 있는 프로젝트에서 다음처럼 실행할 수 있습니다.

```powershell
mvn exec:java '-Dexec.mainClass=com.microsoft.playwright.CLI' '-Dexec.args=install chromium'
```

Codegen으로 브라우저에서 한 동작을 코드로 기록해 볼 수도 있습니다.[6]

```powershell
mvn exec:java '-Dexec.mainClass=com.microsoft.playwright.CLI' '-Dexec.args=codegen https://playwright.dev'
```

생성된 코드는 출발점입니다. 입력 데이터, 검증 조건, 테스트 간 독립성은 직접 정리해야 합니다.

## 어떤 기준으로 선택하면 좋을까?

Java·JUnit 환경에서 화면 검증을 추가하려면 공식 Java API가 있는 Playwright를 검토하기 편합니다. 기존 Node.js 자동화가 Puppeteer로 안정적으로 동작한다면, 새 도구로 옮길 필요가 있는지부터 따져보면 됩니다.

도구 이름보다 먼저 정할 것은 **대상 브라우저, 사용할 언어, 반복 검증할 시나리오**입니다. AI 에이전트에 연결할 때도 같은 기준이 유효합니다.
