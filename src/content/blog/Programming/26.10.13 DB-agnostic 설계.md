## 핵심 요약

- DB-agnostic은 특정 DB 제품에 대한 의존을 줄여, 지원하는 여러 DB에서 같은 기능을 제공하도록 설계한다는 뜻입니다.
- 공통 SQL을 사용하거나, DB별 차이를 저장소 구현과 ORM 같은 경계 안에 격리할 수 있습니다.
- 같은 SQL이 실행되더라도 결과의 의미와 성능까지 같다고 보장되지는 않습니다. 지원 대상 DB에서 검증해야 합니다.

## 두 DB를 지원할 때 생기는 질문

Oracle용 프로그램과 MySQL용 프로그램을 하나로 합친다고 가정해 보겠습니다. 업무는 같은데 NULL 처리 함수, 날짜 계산, 식별자 생성, 페이지 조회 SQL이 서로 다를 수 있습니다.

이때 DB-agnostic, 즉 **데이터베이스 독립적인 설계**는 DB 선택이 바뀌더라도 업무 코드가 받는 영향을 줄이려는 접근입니다. 모든 DB를 무조건 지원한다는 뜻은 아닙니다. 먼저 Oracle 19c와 MySQL 8.4처럼 지원할 제품과 버전을 정해야 합니다.

## 공통 SQL로 차이 줄이기

이름이 NULL이면 `Unknown`을 표시하려고 합니다. 문자열 컬럼 `user_name`이 있는 `app_users` 테이블을 가정한 예제입니다.

Oracle에서는 다음처럼 작성할 수 있습니다.

```sql
SELECT NVL(user_name, 'Unknown') AS display_name
FROM app_users;
```

MySQL에서는 `IFNULL()`을 사용할 수 있습니다.

```sql
SELECT IFNULL(user_name, 'Unknown') AS display_name
FROM app_users;
```

두 DB가 지원하는 `COALESCE()`를 사용하면 이 부분의 SQL을 공통으로 작성할 수 있습니다.[1][2]

```sql
SELECT COALESCE(user_name, 'Unknown') AS display_name
FROM app_users;
```

`COALESCE()`는 인자 중 처음으로 NULL이 아닌 값을 반환합니다. 다만 함수 이름을 통일했다고 타입 변환이나 모든 입력값의 의미까지 같아지는 것은 아닙니다.

대표적인 차이는 빈 문자열입니다. Oracle 19c는 길이가 0인 문자 값을 NULL로 취급합니다.[3] MySQL에서는 빈 문자열과 NULL이 구분됩니다.[5] 따라서 빈 문자열에도 같은 기본값을 표시해야 한다면, 입력 정규화와 저장 정책까지 함께 정해야 합니다.

## DB별 분기가 있으면 독립적이지 않은가?

DB별 구현이 있다는 사실만으로 DB 독립성이 사라지지는 않습니다. **어느 계층에서 차이를 처리하는가**가 중요합니다.

| 설계 | DB를 바꿀 때 살펴볼 곳 |
| --- | --- |
| 서비스 곳곳에서 DB 종류를 확인하고 SQL 선택 | 여러 업무 로직과 SQL |
| 공통 SQL로 지원 범위를 맞춤 | 공통 쿼리의 호환성과 실행 계획 |
| 공통 저장소 계약 아래에 DB별 구현 배치 | 해당 DB의 저장소 구현과 연결 설정 |

예를 들어 서비스가 `MemberRepository.findById()`를 호출하고, DB별 쿼리는 저장소 구현 안에서 처리하도록 만들 수 있습니다. 구현 내부는 DB에 종속되더라도, 서비스를 그 차이로부터 분리할 수 있습니다.

반대로 Oracle과 MySQL에서 실행된다는 사실만으로 업무 코드의 독립성이 높은 것은 아닙니다. DB별 조건문이 여러 계층에 흩어져 있다면 변경과 검증 비용이 커집니다.

## JPA와 Hibernate가 도와주는 범위

다음은 `Member`라는 JPA 엔티티가 매핑되어 있고, `entityManager`를 사용할 수 있는 코드 안의 JPQL 예제입니다.

```java
List<Member> members = entityManager
    .createQuery("SELECT m FROM Member m", Member.class)
    .getResultList();
```

JPQL은 테이블 이름 대신 엔티티와 속성을 기준으로 조회를 표현합니다. Hibernate는 DB의 SQL 방언을 다루는 `Dialect`를 통해 DB별 SQL 생성 차이를 처리합니다.[4]

이것이 ORM이 DB 독립성을 높이는 한 가지 방법입니다. 그러나 다음 항목은 여전히 확인해야 합니다.

- 직접 작성한 네이티브 SQL이나 특정 DB 함수
- 자동 증가·시퀀스 등 식별자 생성 전략
- 날짜·시간과 숫자 타입의 매핑
- 잠금, 트랜잭션 격리 수준과 동시성 동작
- DB 버전별 지원 기능과 조회 성능

ORM으로 표현할 수 있는 범위와 DB가 실제로 지원하는 범위가 다를 수 있습니다. JPA 사용 자체를 완전한 이식성의 증거로 삼기는 어렵습니다.

## 통합 작업에서 먼저 정할 것

| 확인 항목 | 결정할 내용 |
| --- | --- |
| 지원 범위 | DB 제품과 최소 버전 |
| 데이터 의미 | NULL·빈 문자열·시간대의 처리 규칙 |
| 차이 처리 위치 | 공통 SQL, ORM, DB별 어댑터의 역할 |
| 식별자 | 생성 위치, 저장 형식, 유일성 제약 |
| 검증 | 각 DB에서 같은 입력의 결과와 실행 계획 확인 |

식별자를 애플리케이션에서 생성하는 것도 DB 함수 의존을 줄이는 선택입니다. 다만 `UUID()`와 `SYS_GUID()`를 단순히 같은 함수로 치환해서는 안 됩니다. 생성 방식과 표현의 차이는 [MySQL·Oracle·Java의 UUID 비교](/blog/programming/uuid-mysql-oracle-java)에서 따로 정리합니다.

DB 독립성은 제품 전용 기능을 전부 포기해야 한다는 규칙보다는, **변경 영향을 통제하는 설계 목표**로 보는 편이 실용적입니다. 공통으로 유지할 계약과 DB별로 최적화할 구현을 정하고, 실제 지원 대상에서 확인하는 과정이 필요합니다.
