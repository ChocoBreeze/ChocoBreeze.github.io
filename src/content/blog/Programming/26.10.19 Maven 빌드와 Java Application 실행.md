## 핵심 요약

- Maven은 지정한 단계와 플러그인 설정에 따라 컴파일·테스트·패키징 등을 수행합니다.
- Eclipse의 Java Application은 Main Class와 런타임 클래스패스를 기준으로 JVM을 실행합니다. 배포 JAR를 미리 만들 필요는 없습니다.
- IDE 실행 성공과 배포 산출물의 실행 성공은 별도로 확인해야 합니다.

## Maven으로 빌드하고 Java Application으로 실행해도 될까?

Eclipse에서 Spring Boot 프로젝트를 개발할 때 사용할 수 있는 일반적인 조합입니다. 두 작업의 역할이 다르기 때문입니다.

| 구분 | Maven Build | Java Application |
| --- | --- | --- |
| 중심 설정 | `pom.xml`, 실행할 phase·goal | 프로젝트, Main Class, 클래스패스, JRE |
| 주 역할 | 빌드 수명주기와 플러그인 작업 실행 | 지정한 `main()`으로 애플리케이션 시작 |
| JAR 생성 | 패키징 설정과 실행 단계에 따라 수행 | 실행 구성 자체가 패키징하는 것은 아님 |
| 입력 | 소스·리소스·의존성·플러그인 설정 | 클래스 파일·리소스·런타임 의존성 |
| 디버깅 | 실행 대상과 별도 디버그 구성에 따라 달라짐 | Debug As로 중단점 사용 가능 |

“Maven Build”라는 이름만으로 어떤 작업을 했는지는 알 수 없습니다. `compile`만 실행했는지, `verify`나 `install`까지 실행했는지 확인해야 합니다.

## Maven은 지정한 단계까지 진행한다

Maven의 기본 빌드 수명주기는 여러 단계로 나뉘며, 뒤쪽 단계를 지정하면 그 앞 단계도 순서대로 수행합니다.[1]

| 명령 | 목적 |
| --- | --- |
| `mvn compile` | 프로젝트의 주 소스 컴파일 |
| `mvn test` | 테스트 단계까지 수행 |
| `mvn package` | 프로젝트의 packaging 형식으로 산출물 생성 |
| `mvn verify` | 패키징 이후 검증 단계까지 수행 |
| `mvn install` | 검증한 산출물을 로컬 Maven 저장소에 설치 |

실제로 어떤 검사나 생성 작업이 수행되는지는 연결된 플러그인과 프로필에 달려 있습니다. 예를 들어 통합 테스트가 자동으로 실행되려면 해당 단계의 플러그인 설정이 필요합니다.

`clean`은 별도의 수명주기입니다. `mvn clean verify`는 기존 빌드 출력을 정리한 뒤 검증 단계까지 실행하는 조합입니다. 매번 로컬 저장소에 설치할 이유가 없다면 `clean install`을 모든 코드 수정마다 실행할 필요는 없습니다.

## Java Application은 생성된 JAR를 실행하는가?

보통은 아닙니다. Eclipse의 Java Application 실행 구성은 프로젝트의 빌드 경로를 바탕으로 클래스패스를 구성하고, 지정한 Main Class를 실행합니다.[2]

Spring Boot 프로젝트라면 `SpringApplication.run(...)`을 호출하는 `main()`이 진입점이 됩니다. 프로젝트의 컴파일 결과와 리소스, 의존성 JAR들이 클래스패스에 있으면 배포용 실행 JAR를 만들지 않고도 시작할 수 있습니다.

Eclipse의 자동 빌드는 변경 사항을 점진적으로 컴파일할 수 있습니다.[5] 다만 컴파일 오류, 실행 전 빌드 설정, 리소스 복사와 생성 코드 설정이 올바른지 확인해야 합니다. Maven 플러그인에서만 수행하는 코드 생성이나 리소스 필터링은 IDE 실행에서 같은 방식으로 수행되지 않을 수 있습니다.

따라서 “저장했으니 실행 중 서버에도 모두 반영되었다”거나 “Maven 빌드 결과와 IDE 컴파일 결과가 항상 같다”라고 가정해서는 안 됩니다.

## JVM 옵션은 실행 대상에 넣기

Java Application의 Arguments 탭에서는 VM arguments와 Program arguments를 구분합니다.[2] 예를 들어 VM arguments에 다음을 넣을 수 있습니다.

```text
-Xmx512m -Dspring.profiles.active=local
```

Spring Boot의 애플리케이션 인자로 프로필을 전달한다면 Program arguments에 다음처럼 넣습니다.

```text
--spring.profiles.active=local
```

반면 `spring-boot:run`은 Maven 플러그인이 별도 프로세스로 애플리케이션을 실행합니다. Maven 프로세스용 옵션과 애플리케이션 JVM용 옵션은 구분해야 합니다.[3]

```bash
mvn spring-boot:run "-Dspring-boot.run.jvmArguments=-Xmx512m"
```

실행 방식이 바뀌었을 때 메모리 설정이나 프로필이 달라진다면, 같은 옵션을 실제 대상 프로세스에 전달했는지 먼저 확인할 수 있습니다.

## 실행 JAR도 따로 확인하기

Spring Boot Maven Plugin의 `repackage`는 의존성을 포함해 `java -jar`로 실행할 수 있는 아카이브를 만듭니다. 단순한 JAR 패키징과는 구분됩니다.[4]

프로젝트에서 `repackage`가 `package` 단계에 연결되어 있다고 가정하면 다음처럼 배포 산출물을 만들고 확인합니다. 파일명은 실제 생성된 JAR로 바꿔야 합니다.

```bash
mvn clean package
java -Xmx512m -jar target/application.jar --spring.profiles.active=local
```

IDE에서 정상 실행되더라도 패키징에서 빠진 리소스, 다른 프로필, 배포 환경의 JDK나 외부 설정 때문에 JAR 실행은 실패할 수 있습니다. 배포할 파일을 실제 배포와 가까운 방식으로 실행하는 검증이 필요합니다.

## 평소 개발에서는 어떻게 나눌까?

평소 코드 수정과 중단점 확인에는 Java Application 또는 Debug As를 사용하고, 빌드 설정을 바꿨거나 배포 전에 Maven 검증과 JAR 실행을 확인하는 흐름을 사용할 수 있습니다.

Debug As에서의 Hot Code Replace도 모든 변경을 무조건 반영하지는 않습니다. 메서드 추가 등 구조 변경의 제약과 DevTools의 재시작 방식은 [DevTools·HCR·JRebel 비교](/blog/programming/devtools-hcr-jrebel)에서 따로 다룹니다.
