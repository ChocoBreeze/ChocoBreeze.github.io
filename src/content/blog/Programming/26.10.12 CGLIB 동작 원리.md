## 핵심 요약

- CGLIB는 런타임에 클래스를 생성하는 라이브러리이며, Spring은 재패키징한 CGLIB를 `spring-core`에 포함합니다.
- 상속과 오버라이드를 이용하므로 `final` 클래스와 메서드, `private` 메서드 등에 제약이 있습니다.
- 직접 만든 CGLIB 예제와 Spring AOP의 일반적인 대상 객체 위임 구조는 구분해서 이해해야 합니다.

## 클래스를 실행 중에 만든다는 뜻

보통 Java에서는 작성한 소스를 컴파일해 클래스를 준비합니다. CGLIB는 실행 중 필요한 하위 클래스를 생성해, 기존 클래스의 메서드 호출에 동작을 덧붙일 수 있습니다.

Spring이 사용하는 `org.springframework.cglib`는 `spring-core`에 재패키징된 구현입니다.[1] 따라서 Spring 프로젝트에서 실험하려고 별도의 오래된 `cglib` 의존성을 무조건 추가할 필요는 없습니다.

## 주요 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| `Enhancer` | 상속할 클래스와 콜백을 지정해 새 클래스·객체 생성 |
| `MethodInterceptor` | 가로챈 메서드 호출을 처리하는 콜백 |
| `MethodProxy` | 원래 구현이나 다른 대상의 메서드를 호출하는 데 사용 |
| `CallbackFilter` | 메서드별로 사용할 콜백 선택 |

`Enhancer`는 메서드를 오버라이드할 수 있는 하위 클래스를 만들고 콜백과 연결합니다.[2] 모든 메서드를 조건 없이 가로챌 수 있는 것은 아닙니다.

## 작은 예제로 확인하기

다음은 `spring-core`가 클래스패스에 있는 Java 프로젝트에서 사용할 예제입니다. 파일 이름은 `CglibDemo.java`이며, 서비스 클래스를 중첩 클래스로 두어 하나의 파일에 담았습니다.

```java
import org.springframework.cglib.proxy.Enhancer;
import org.springframework.cglib.proxy.MethodInterceptor;

public class CglibDemo {
    public static class OrderService {
        public String order(String item) {
            return "주문 완료: " + item;
        }
    }

    public static void main(String[] args) {
        Enhancer enhancer = new Enhancer();
        enhancer.setSuperclass(OrderService.class);
        enhancer.setCallback((MethodInterceptor) (obj, method, params, proxy) -> {
            System.out.println("before: " + method.getName());
            Object result = proxy.invokeSuper(obj, params);
            System.out.println("after: " + method.getName());
            return result;
        });

        OrderService service = (OrderService) enhancer.create();
        System.out.println(service.order("부품"));
    }
}
```

호출 흐름을 보여주는 출력은 다음과 같습니다.

```text
before: order
after: order
주문 완료: 부품
```

`invokeSuper()`는 생성된 객체에서 부모의 원래 구현을 호출합니다.[3] 콜백 안에서 같은 프록시 메서드를 평범하게 다시 호출하면 재귀적으로 콜백에 들어갈 수 있으므로, 원래 구현을 부르는 경로를 구분해야 합니다.

## Spring AOP는 보통 별도의 대상 객체로 위임한다

위 예제에는 별도로 만든 원본 `OrderService`가 없습니다. 생성한 객체에서 부모 구현을 실행합니다.

반면 일반적인 Spring AOP 구성에서는 프록시와 대상 객체가 구분됩니다. 프록시는 Advice를 실행하고 대상 객체의 업무 메서드로 위임합니다. 따라서 대상 내부의 `this.otherMethod()` 호출은 프록시를 다시 통과하지 않아 Advice를 건너뛸 수 있습니다.[1]

예를 들어 외부에서 `dispatch()`를 호출하고 그 안에서 `this.assignJob()`을 호출한다면, `assignJob()`에 `@Transactional`을 붙였다는 사실만으로 새로운 트랜잭션 경계가 적용되지는 않습니다. 이때 실제 트랜잭션 유무는 바깥 호출의 설정에도 달려 있습니다.

## 상속 기반이므로 생기는 제약

| 대상 | CGLIB 기반 AOP에서 확인할 점 |
| --- | --- |
| `final` 클래스 | 상속 불가 |
| `final` 메서드 | 오버라이드 불가, Advice 적용 불가 |
| `private` 메서드 | 오버라이드 대상이 아님 |
| `static` 메서드 | 인스턴스 오버라이드 방식으로 가로채는 대상이 아님 |
| package-private 메서드 | 패키지와 클래스 로더에 따른 가시성 확인 필요 |

Spring은 보통 Objenesis를 사용해 프록시 객체의 생성자 호출을 우회합니다.[1] 그렇다고 모든 프록시의 필드가 항상 `null`이라고 일반화해서는 안 됩니다. 중요한 것은 **프록시와 실제 대상 객체의 상태가 같다고 가정하지 않는 것**입니다. 프록시의 `final` 메서드를 직접 호출할 때 생길 수 있는 문제는 [DaoSupport 로그 분석](/blog/programming/cglib-final-method-daosupport)에서 다룹니다.

## @Configuration도 같은 방식일까?

Spring은 전체 설정 처리를 적용하는 `@Configuration` 클래스에도 CGLIB 향상을 사용합니다. 여기서는 `@Bean` 메서드 사이의 호출을 컨테이너 관리와 연결하는 목적이 있습니다.[4] 일반적인 AOP 대상 위임 구조를 그대로 대입하면 헷갈릴 수 있습니다.

`@Configuration(proxyBeanMethods = false)`는 이런 메서드 간 호출 가로채기를 끕니다. 그렇다고 애플리케이션 전체의 트랜잭션 AOP가 꺼지는 것은 아닙니다.

## JDK 동적 프록시와 비교

| 항목 | JDK 동적 프록시 | CGLIB 기반 프록시 |
| --- | --- | --- |
| 주요 방식 | 인터페이스 구현 | 클래스 상속 |
| 호출 대상으로 노출하는 API | 프록시 인터페이스 | 상속받은 클래스의 API |
| 구체 구현 클래스 타입으로 취급 | 일반적으로 불가 | 가능한 경우가 많음 |
| 구현 클래스의 `final` 메서드 | 인터페이스 경유 위임과 구분 | 가로채기 불가 |

둘 중 하나가 항상 빠르다는 결론부터 내릴 필요는 없습니다. 사용하는 JVM, Advice와 호출 경로에 따라 달라지므로 성능은 실제 조건에서 측정해야 합니다. 우선은 프록시를 통과하는 호출과 그렇지 않은 호출을 구분하는 것이 AOP 문제를 이해하는 데 더 도움이 됩니다.
