## 핵심 요약

- DevTools는 주로 애플리케이션을 자동 재시작해 변경을 반영합니다.
- Eclipse HCR은 디버깅 중 JVM의 클래스 교체 기능을 사용하며, 기본적인 환경에서는 메서드 본문 변경을 중심으로 활용합니다.
- JRebel은 더 넓은 변경을 재배포 없이 반영하기 위한 도구지만, 지원 범위와 실행 설정을 확인해야 합니다.

## 저장했더니 바뀌었다고 모두 같은 기능은 아니다

Java 코드를 저장한 뒤 새 결과가 나온다고 해서 어떤 기능이 동작했는지 바로 알 수는 없습니다. IDE가 컴파일하고 DevTools가 재시작했을 수도 있고, 디버거가 변경된 클래스를 실행 중인 JVM에 전달했을 수도 있습니다.

프런트엔드 도구에서 말하는 HMR(Hot Module Replacement)과 Java 개발 환경의 변경 반영을 같은 이름으로 부르면 이 차이가 가려집니다. 먼저 **자동으로 다시 시작했는지, 실행 중 코드를 교체했는지**를 구분하는 것이 좋습니다.

| 구분 | Spring Boot DevTools | Eclipse HCR | JRebel |
| --- | --- | --- | --- |
| 주된 접근 | 변경 감지 후 애플리케이션 재시작 | 디버거를 통한 클래스 재정의 | Java agent 기반 재로딩 |
| 동작 조건 | DevTools와 클래스패스 변경 | Debug 연결과 JVM의 지원 | Agent 실행, 라이선스·프로젝트 설정 등 |
| 메서드 본문 변경 | 재시작 후 반영 | 일반적인 활용 범위 | 지원 |
| 메서드·필드 추가 | 재시작 후 반영 | 기본 HotSwap에서는 제약 | 더 넓게 지원하나 제한 확인 필요 |
| 초기화·메모리 상태 | 재시작에 따라 다시 구성 | 기존 객체·상태가 남을 수 있음 | 변경 종류와 프레임워크 연동에 따라 다름 |

## DevTools: JVM 종료와 다른 자동 재시작

DevTools의 재시작은 보통 JVM 프로세스를 통째로 종료하고 새로 실행하는 방식과 다릅니다. 변경이 적은 라이브러리와 개발 중인 클래스를 서로 다른 클래스 로더로 나누고, 재시작 때 개발 코드 쪽 클래스 로더를 새로 구성합니다.[1]

이 때문에 완전한 기동보다 빠를 수 있지만, Spring 컨텍스트와 관련 초기화 작업을 다시 수행하는 비용은 남습니다.

또한 감지 대상은 일반적으로 클래스패스의 변경입니다. 소스 파일을 저장해도 컴파일 결과가 갱신되지 않으면 기대한 재시작이 일어나지 않을 수 있습니다. IDE의 자동 빌드나 실제 클래스 출력 경로를 함께 봐야 합니다.

## HCR: 메서드 본문을 바꿀 때 유용한 디버깅 기능

Eclipse의 Hot Code Replace(HCR)는 디버깅 중 변경된 클래스를 JVM에 반영하는 기능입니다.[2] 예를 들어 다음 메서드의 반환 문자열을 바꾸는 수정은 일반적인 활용 사례입니다.

```java
public String getName() {
    return "홍길동";
}
```

```java
public String getName() {
    return "김철수";
}
```

반면 메서드나 필드 추가, 상속 관계 변경처럼 클래스의 구조를 바꾸는 작업은 기본적인 HotSwap의 지원 범위를 벗어날 수 있습니다. 정확한 범위는 디버거가 연결된 JVM의 기능에 달려 있으며, JDI API도 메서드 추가와 클래스 재정의 지원 여부를 따로 조회하도록 되어 있습니다.[3]

코드가 교체되어도 기존 객체의 생성자와 초기화 과정이 자동으로 다시 실행되는 것은 아닙니다. 이미 읽어 둔 설정이나 필드 값까지 바뀐다고 기대하면 안 됩니다.

## JRebel: 재로딩 범위를 넓히는 도구

JRebel은 Java agent로 동작하며, 실행 중 클래스와 지원되는 프레임워크 설정의 변경 반영을 돕습니다.[4] 기본 HotSwap보다 넓은 변경을 다룰 수 있어 재기동 비용이 큰 프로젝트에서 검토할 만합니다.

다만 “모든 변경을 재시작 없이 반영한다”는 보장은 아닙니다. 이미 만들어진 객체의 생성자·초기화 코드 변경처럼 객체 재생성이 필요한 상황도 있습니다.[5] JRebel이 활성화되었다는 표시와 실제 변경이 반영됐다는 검증을 구분해야 합니다.

JRebel 자체가 Java 소스를 컴파일해 주는 것도 아닙니다. 공식 Eclipse 안내는 컴파일 결과를 이용하므로 자동 빌드 설정을 확인하도록 설명합니다.[6]

## 현재 환경을 확인하는 순서

1. **실행 모드를 봅니다.** Debug 모드에서만 반영되는지 확인합니다.
2. **로그를 봅니다.** 컨텍스트 초기화나 서버 기동 로그가 반복되는지 살펴봅니다.
3. **컴파일을 확인합니다.** 저장 후 수정한 클래스의 출력물이 갱신되는지 봅니다.
4. **실행 인자를 봅니다.** JRebel agent가 실제로 붙어 있는지 확인합니다.
5. **변경 종류를 나눠 봅니다.** 메서드 본문 수정과 구조 변경을 구분해 확인합니다.

HCR로 필요한 변경을 충분히 반영하고 재시작도 부담되지 않는다면, JRebel을 추가할 이유는 크지 않을 수 있습니다. 재시작이 얼마나 자주 발생하고 얼마나 오래 걸리는지 측정한 뒤, 지원 범위와 비용을 비교하는 편이 현실적입니다.

프로젝트에 JRebel Nature가 남아 있다는 사실만으로 실행 중인 JRebel의 유무를 판단할 수는 없습니다. 이 차이는 [Eclipse Nature와 JRebel의 역할](/blog/programming/eclipse-nature-jrebel)에서 이어서 다룹니다.
