## 핵심 요약

- Checkstyle과 JaCoCo는 둘 다 **코드 품질을 자동으로 검사하는 Maven 플러그인**입니다. pom.xml에 설정해 두면 빌드 중에 검사가 돌고, 기준을 어기면 빌드를 실패시킬 수 있습니다.
- Checkstyle은 **코딩 스타일**을, JaCoCo는 **테스트 커버리지**를 검사합니다.
- 두 플러그인의 `check` goal은 기본적으로 **verify 단계**에 연결됩니다. 그래서 `package`까지만 실행하면 돌지 않고, `verify`나 그 뒤 단계(`install`, `deploy`)를 실행해야 동작합니다.
- 기본 상태의 Maven 프로젝트에는 이런 검사가 **하나도 없습니다.** 누군가 pom.xml에 추가해야만 동작합니다.

Maven의 phase와 "앞 단계가 모두 먼저 실행된다"는 규칙은 [IntelliJ Maven 탭의 Lifecycle 항목은 무엇인가](/blog/programming/maven-lifecycle-phases)에서 정리했습니다.

## Checkstyle: 코딩 스타일 검사

코드가 **정해진 작성 규칙을 지키는지** 검사합니다. 프로그램 동작에는 영향이 없지만, 팀 코드를 일관되게 유지하는 데 씁니다.

- 들여쓰기, 한 줄 길이 제한(예: 120자)
- 이름 규칙(클래스는 PascalCase, 상수는 UPPER_SNAKE_CASE)
- 쓰지 않는 import, `*` import 금지
- 중괄호 위치, public 메서드에 Javadoc 필수 여부 등

규칙 세트는 직접 만들 수도 있고, 공개 규칙을 가져다 쓸 수도 있습니다. `maven-checkstyle-plugin`에는 Sun 스타일(`sun_checks.xml`, 기본값)과 Google Java Style(`google_checks.xml`) 규칙 파일이 들어 있습니다.[1]

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-checkstyle-plugin</artifactId>
    <version>3.6.0</version>
    <configuration>
        <configLocation>google_checks.xml</configLocation>
        <violationSeverity>warning</violationSeverity>
    </configuration>
    <executions>
        <execution>
            <id>checkstyle-check</id>
            <goals><goal>check</goal></goals>
        </execution>
    </executions>
</plugin>
```

`<phase>`를 적지 않으면 `check` goal은 기본 단계인 verify에 연결됩니다. 더 일찍 실패시키고 싶다면 `<phase>validate</phase>`처럼 앞 단계에 직접 연결하는 프로젝트도 많습니다. 이 경우에는 `compile`만 실행해도 스타일 검사가 먼저 돕니다.

위반이 있어도 빌드가 실패하는지는 **규칙의 심각도**(severity)와 `violationSeverity` 설정에 따라 달라집니다. 기본값은 `error` 수준 위반만 빌드를 실패시키므로, 규칙 파일이 위반을 `warning`으로 보고하면 경고만 출력하고 넘어갈 수 있습니다. 위 예시처럼 `violationSeverity`를 `warning`으로 낮추면 경고 수준 위반에서도 빌드가 실패합니다. 플러그인 버전은 실제 프로젝트에서 쓰는 버전에 맞춰 바꾸면 됩니다.

## JaCoCo: 테스트 커버리지 측정

테스트를 실행할 때 **코드의 몇 퍼센트가 실제로 실행됐는지** 측정합니다. JaCoCo는 세 goal을 함께 씁니다.[2]

| Goal | 기본 단계 | 하는 일 |
| --- | --- | --- |
| `prepare-agent` | initialize | 테스트를 실행하는 JVM에 JaCoCo 에이전트를 붙여 실행 기록(`target/jacoco.exec`)을 남기게 합니다 |
| `report` | verify | 어느 줄과 분기가 테스트되지 않았는지 HTML 리포트로 보여줍니다(`target/site/jacoco/index.html`). 빨간색과 초록색으로 표시돼 보기 편합니다 |
| `check` | verify | "라인 커버리지 80% 미만이면 빌드 실패" 같은 기준을 강제합니다 |

`prepare-agent`가 빠지면 실행 기록이 없어서 `report`와 `check`가 할 일이 없습니다. 커버리지 기준을 강제하는 전체 설정은 다음과 같습니다.

```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.12</version>
    <executions>
        <execution>
            <id>prepare-agent</id>
            <goals><goal>prepare-agent</goal></goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>verify</phase>
            <goals><goal>report</goal></goals>
        </execution>
        <execution>
            <id>check</id>
            <phase>verify</phase>
            <goals><goal>check</goal></goals>
            <configuration>
                <rules>
                    <rule>
                        <element>BUNDLE</element>
                        <limits>
                            <limit>
                                <counter>LINE</counter>
                                <value>COVEREDRATIO</value>
                                <minimum>0.80</minimum>
                            </limit>
                        </limits>
                    </rule>
                </rules>
            </configuration>
        </execution>
    </executions>
</plugin>
```

`BUNDLE`은 모듈 전체를 하나로 보고 기준을 적용한다는 뜻입니다. `CLASS`나 `PACKAGE`로 바꾸면 클래스나 패키지마다 기준을 따로 검사합니다. `LINE` 대신 `BRANCH`를 쓰면 if/else 같은 분기 커버리지를 기준으로 삼습니다.

### 테스트를 건너뛰면 JaCoCo는 어떻게 될까

JaCoCo는 테스트 실행 결과를 바탕으로 커버리지를 계산합니다. 그래서 `-DskipTests`로 테스트를 건너뛰면 측정할 데이터가 없어서 `report`와 `check`가 대부분 그냥 건너뜁니다. 이때 로그에는 "Skipping JaCoCo execution due to missing execution data file" 같은 메시지가 출력됩니다.

단, `clean` 없이 빌드하면 이전 빌드에서 남은 `target/jacoco.exec`를 그대로 읽어 오래된 데이터로 리포트나 검사를 할 수 있습니다. 커버리지를 정확히 보려면 `clean verify`처럼 `clean`과 함께 실행하는 편이 안전합니다. 참고로 Failsafe도 `-DskipTests`를 따르며, 통합 테스트만 건너뛰려면 `-DskipITs`를 씁니다.

따라서 `install -DskipTests`처럼 테스트를 건너뛴 빌드가 품질 검사에서 실패했다면, 원인은 JaCoCo보다 **Checkstyle 같은 정적 검사**일 가능성이 높습니다. 정적 검사는 테스트 실행과 상관없이 소스 코드만 보고 돌기 때문입니다.

## Checkstyle과 JaCoCo 비교

| 구분 | Checkstyle | JaCoCo |
| --- | --- | --- |
| 검사 대상 | 소스 코드의 작성 형식 | 테스트가 실제로 실행한 코드의 비율 |
| 테스트 실행 필요 | 아니요 | 예 |
| 대표 실패 원인 | 줄 길이 초과, 이름 규칙 위반, 쓰지 않는 import | 커버리지가 기준 미만 |
| 결과물 | 위반 목록(콘솔, `target/checkstyle-result.xml`) | `target/jacoco.exec`, HTML 리포트 |
| `-DskipTests`일 때 | 그대로 실행됨 | 데이터가 없어 대부분 건너뜀 |

## 같은 부류의 다른 도구들

| 도구 | 검사 내용 |
| --- | --- |
| **SpotBugs** | 버그 패턴 탐지 (null 역참조 가능성, equals/hashCode 불일치, 닫지 않은 리소스 등) |
| **PMD** | 나쁜 코드 패턴 탐지 (빈 catch 블록, 쓰지 않는 변수, 너무 복잡한 메서드) |
| **Failsafe** | 통합 테스트 실행 (기본으로 `*IT.java` 등). 단위 테스트는 Surefire, 통합 테스트는 Failsafe가 담당합니다 |
| **SonarQube** | 위 검사들을 서버에서 종합 분석하고 대시보드로 보여줍니다. 빌드 플러그인이라기보다 별도 서버이고, `mvn sonar:sonar`로 분석 결과를 보냅니다 |

Failsafe는 품질 검사 도구라기보다 테스트 실행 도구입니다. 통합 테스트는 `integration-test` 단계에서 실행하고, 실패 여부는 verify 단계에서 판정합니다. 그래서 통합 테스트가 실패해도 서버 정리 같은 후처리(`post-integration-test`)가 먼저 실행될 수 있습니다.[3]

SonarQube는 커버리지를 직접 측정하지 않습니다. 보통 JaCoCo가 만든 리포트를 읽어서 대시보드에 표시하므로, 두 도구를 함께 씁니다.

## 우리 프로젝트에 설정돼 있는지 확인하는 방법

다음 방법으로 직접 확인할 수 있습니다.

- pom.xml의 `<build><plugins>`에 `maven-checkstyle-plugin`, `jacoco-maven-plugin` 같은 항목이 있는지 봅니다.
- 부모 pom에서 상속받은 설정까지 포함해 보려면 실제로 적용되는 pom(effective pom)을 출력합니다.

**PowerShell**

```powershell
.\mvnw.cmd help:effective-pom "-Doutput=effective-pom.xml"
```

**CMD**

```bat
mvnw.cmd help:effective-pom -Doutput=effective-pom.xml
```

PowerShell에서는 `.`이나 `=`가 들어간 `-D` 인자를 따옴표로 감싸야 Maven에 제대로 전달됩니다. Maven Wrapper가 없는 프로젝트라면 `mvnw.cmd` 대신 `mvn`을 쓰면 됩니다.

만들어진 `effective-pom.xml`에서 `checkstyle`, `jacoco`, `spotbugs`, `pmd`를 검색하고, 그 플러그인의 `<execution>`에 어떤 `<phase>`와 `<goal>`이 연결돼 있는지 보면 언제 검사가 도는지 알 수 있습니다.

IntelliJ에서는 pom.xml을 우클릭한 뒤 **Maven → Show Effective POM**으로도 볼 수 있습니다.
