## 핵심 요약

- IntelliJ 오른쪽 **Maven 탭 → Lifecycle**에 보이는 `clean, validate, compile, test, package, verify, install, site, deploy`는 **Maven 빌드 라이프사이클의 phase(단계)**입니다.
- Maven에는 서로 독립된 라이프사이클이 **clean, default, site** 세 개 있고, IntelliJ는 이 중 대표 phase를 한 목록에 섞어서 보여줍니다.
- default 라이프사이클에서 어떤 phase를 실행하면 **그 앞의 phase가 모두 순서대로 먼저 실행**됩니다.
- `deploy`는 서버에 애플리케이션을 배포하는 기능이 아니라, 만든 산출물을 **원격 Maven 저장소**에 올리는 단계입니다.

## 라이프사이클 3개

| 라이프사이클 | IntelliJ에 보이는 phase | 역할 |
| --- | --- | --- |
| **clean** | clean | 이전 빌드 결과 삭제 |
| **default** | validate → compile → test → package → verify → install → deploy | 실제 빌드와 배포 |
| **site** | site | 프로젝트 문서 사이트 생성 |

실제 Maven 라이프사이클에는 `process-resources`, `test-compile`, `integration-test` 같은 중간 phase가 더 있습니다.[1] IntelliJ의 Lifecycle 목록은 그중 자주 쓰는 대표 phase만 보여줍니다.

가장 중요한 규칙은 이것입니다. **default 라이프사이클에서 어떤 phase를 실행하면 그 앞의 phase가 모두 순서대로 실행됩니다.** 예를 들어 `install`을 실행하면 validate → compile → test → package → verify → install이 전부 돌아갑니다.

반면 라이프사이클끼리는 독립적이라서, `package`를 실행해도 `clean`은 자동으로 실행되지 않습니다. 이전 결과를 지우고 싶으면 `clean package`처럼 직접 함께 지정해야 합니다.

## 각 phase 설명

| Phase | 하는 일 | 결과물 / 비고 |
| --- | --- | --- |
| **clean** | `target/` 디렉터리를 삭제합니다 | 이전 빌드 결과가 남아 생기는 문제를 없앨 때 씁니다 |
| **validate** | 프로젝트 구조와 필요한 정보가 올바른지 검사합니다 | 컴파일은 하지 않습니다. 기본 설정에서는 연결된 goal이 거의 없습니다 |
| **compile** | `src/main/java`를 컴파일합니다 | `target/classes` |
| **test** | `src/test/java`를 컴파일하고 단위 테스트를 실행합니다(Surefire 플러그인) | 테스트가 하나라도 실패하면 빌드가 중단됩니다 |
| **package** | 컴파일 결과를 패키징합니다 | `target/xxx.jar` 또는 `.war`. Spring Boot는 `spring-boot-maven-plugin`의 `repackage`가 이 단계에 연결되어 **실행 가능한 fat jar**를 만듭니다 |
| **verify** | 통합 테스트 결과 확인(Failsafe 플러그인), 품질 검사(Checkstyle, JaCoCo 커버리지 기준 등)를 실행합니다 | 설정해 둔 플러그인이 없으면 사실상 하는 일이 없습니다 |
| **install** | 만든 jar를 **로컬 저장소**에 복사합니다 | Windows 기준 `%USERPROFILE%\.m2\repository`. 같은 PC의 다른 프로젝트가 이 모듈을 dependency로 쓸 수 있게 됩니다 |
| **site** | 프로젝트 문서 HTML(의존성 목록, 리포트 등)을 만듭니다 | `target/site`. 실무에서는 거의 쓰지 않습니다 |
| **deploy** | jar를 **원격 저장소**(Nexus, Artifactory 등)에 업로드합니다 | pom.xml의 `<distributionManagement>`와 settings.xml의 인증 정보가 필요합니다 |

`deploy`라는 이름 때문에 운영 서버 배포로 오해하기 쉽습니다. 실제로는 "만든 라이브러리를 사내 저장소에 올린다"는 뜻입니다. 애플리케이션을 서버에 올리는 일은 보통 CI/CD 파이프라인이나 별도 배포 도구가 맡습니다.

Spring Boot의 `repackage`는 `spring-boot-starter-parent`를 부모로 쓰거나 플러그인에 `repackage` 실행을 직접 설정했을 때 `package` 단계에서 동작합니다.[2] 그렇지 않으면 `package`는 의존성이 빠진 일반 jar만 만듭니다.

## 자주 쓰는 조합

아래 예시는 프로젝트에 Maven Wrapper(`mvnw`, `mvnw.cmd`)가 있다고 가정합니다. Wrapper가 없다면 `mvnw.cmd` 대신 설치된 `mvn`을 쓰면 됩니다.

**PowerShell**

```powershell
# 깨끗하게 다시 빌드해서 jar 만들기 (가장 많이 씀)
.\mvnw.cmd clean package

# 테스트를 건너뛰고 빌드 (테스트 컴파일은 함)
.\mvnw.cmd clean package -DskipTests

# 테스트 컴파일까지 건너뛰기 - PowerShell에서는 따옴표가 필요함
.\mvnw.cmd clean package "-Dmaven.test.skip=true"

# 멀티모듈에서 공통 모듈을 로컬 저장소에 등록
.\mvnw.cmd clean install
```

**CMD**

```bat
mvnw.cmd clean package
mvnw.cmd clean package -DskipTests
mvnw.cmd clean package -Dmaven.test.skip=true
mvnw.cmd clean install
```

`-DskipTests`와 `-Dmaven.test.skip=true`는 다릅니다.

| 옵션 | 테스트 컴파일 | 테스트 실행 |
| --- | --- | --- |
| `-DskipTests` | 함 | 안 함 |
| `-Dmaven.test.skip=true` | 안 함 | 안 함 |

다른 모듈이 테스트 jar(`test-jar`)에 의존하는 프로젝트라면 `maven.test.skip`은 그 jar도 만들지 않으므로 빌드가 깨질 수 있습니다. 일반적으로는 `-DskipTests`가 더 안전합니다.[3]

### PowerShell에서 따옴표가 필요한 이유

PowerShell에서는 `-Dmaven.test.skip=true`처럼 `.`이나 `=`가 들어간 인자를 따옴표로 감싸야 합니다. 그렇지 않으면 PowerShell이 인자를 잘못 쪼개서 Maven이 `Unknown lifecycle phase ".test.skip=true"` 같은 오류를 냅니다. CMD나 bash에서는 따옴표 없이도 그대로 전달됩니다.

## IntelliJ에서 쓸 때 팁

- **여러 개를 한 번에 실행하기**: Ctrl을 누른 채 `clean`과 `package`를 함께 선택하고 실행하면 `clean package`로 한 번에 돌아갑니다.
- **테스트 건너뛰기 토글**: Maven 탭 상단 툴바의 "Toggle 'Skip Tests' Mode" 버튼(번개 모양 아이콘, 버전에 따라 모양은 다를 수 있음)을 켜 두면 lifecycle을 실행할 때마다 테스트를 건너뜁니다. 켜 둔 것을 잊으면 테스트가 실패해도 알아차리지 못하니 주의합니다.

### 언제 무엇을 쓸지

| 상황 | 추천 명령 |
| --- | --- |
| 실행 가능한 jar가 필요할 때 | `clean package` |
| 멀티모듈에서 공통 모듈을 고친 뒤 다른 프로젝트가 그걸 못 찾을 때 | `clean install` |
| CI에서 커밋 품질을 확인할 때 | `clean verify` |

CI에서는 `install`보다 `verify`를 권장합니다. `install`은 로컬 저장소를 건드리기 때문에, 병렬 빌드나 캐시를 공유하는 환경에서 다른 빌드에 영향을 줄 수 있습니다. Maven 공식 문서도 무엇을 실행할지 모르겠다면 `mvn verify`를 권장합니다.[1]

## 참고: Lifecycle과 Plugins의 차이

같은 Maven 탭의 **Plugins** 항목에 있는 `spring-boot:run`, `dependency:tree` 같은 것은 phase가 아니라 **플러그인 goal**입니다.

- **phase**: "어디까지 진행할지"를 정하는 단계입니다. phase 자체는 아무 일도 하지 않고, 연결된 goal이 실제 작업을 합니다.
- **goal**: 실제 작업 단위입니다. 예를 들어 compile phase에는 `compiler:compile` goal, test phase에는 `surefire:test` goal이 연결되어 있습니다.

goal을 직접 실행하면 앞 단계를 거치지 않고 그 작업 하나만 수행합니다. 그래서 `dependency:tree`는 컴파일 없이 바로 의존성 트리를 보여줍니다. 반대로 컴파일된 결과가 필요한 goal은 앞 단계를 먼저 실행해 둬야 할 수 있습니다.

Maven 빌드와 IDE의 Java Application 실행이 어떻게 다른지는 [Maven 빌드와 Java Application 실행은 무엇이 다를까?](/blog/programming/maven-build-java-application)에서 다룹니다.
