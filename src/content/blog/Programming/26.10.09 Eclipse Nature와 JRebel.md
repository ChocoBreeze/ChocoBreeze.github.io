## 핵심 요약

- Nature는 Eclipse가 프로젝트에 특정 기능을 연결하기 위한 메타데이터입니다.
- JRebel Nature는 IDE의 프로젝트 설정이며, 실행 중 JVM에 JRebel이 활성화됐다는 증거는 아닙니다.
- 설정을 정리하기 전에는 팀의 사용 여부와 실행 구성을 확인하고, Java·Maven 관련 설정을 함께 지우지 않도록 범위를 좁혀야 합니다.

## Nature는 프로젝트의 성격을 Eclipse에 알려준다

Eclipse는 여러 언어와 도구를 플러그인으로 지원합니다. 프로젝트가 어떤 도구의 관리를 받아야 하는지 표현하는 장치 중 하나가 **Project Nature**입니다. 공식 문서는 Java 개발 도구가 Java Nature를 통해 프로젝트에 Java 기능을 연결하는 사례를 듭니다.[1]

프로젝트의 `.project` 파일에서는 다음과 같은 형태를 볼 수 있습니다. 아래는 구조를 설명하는 일부 예시이며, 실제 프로젝트에는 다른 항목도 함께 있습니다.

```xml
<natures>
    <nature>org.eclipse.jdt.core.javanature</nature>
</natures>
```

이 설정은 Java 런타임 라이브러리를 추가하는 Maven 의존성과 다릅니다. Eclipse가 프로젝트를 어떻게 다룰지 정하는 정보입니다.

## Nature와 Builder는 어떻게 다를까?

Nature는 프로젝트의 기능 구성을 나타내며, 필요한 Builder를 설정하는 등 프로젝트 환경을 구성할 수 있습니다.[1] Builder는 빌드 과정에 참여하는 실행 단위입니다.

| 구분 | 주요 역할 | 확인 위치 예시 |
| --- | --- | --- |
| Nature | 프로젝트에 도구별 성격·기능 연결 | `.project`의 `natures` |
| Builder | 빌드 과정의 작업 수행 | `.project`의 `buildSpec` |
| Java Build Path | 소스·클래스패스 구성 | `.classpath`, 프로젝트 속성 |
| Maven 의존성 | 빌드·실행에 필요한 라이브러리 선언 | `pom.xml` |

서로 연동될 수는 있지만 같은 설정은 아닙니다. Eclipse에서 특정 Nature를 찾지 못한다는 문제와 Maven에서 라이브러리를 받지 못한다는 문제는 원인부터 나누어 확인해야 합니다.

## JRebel Nature가 하는 일

JRebel의 Eclipse 플러그인은 프로젝트 설정을 돕습니다. 공식 안내에 따르면 JRebel Nature를 활성화하면 `rebel.xml`을 생성할 수 있습니다. 이 파일은 실행 애플리케이션과 개발 작업 공간의 클래스·리소스 위치를 연결하는 데 사용됩니다.[2][3]

다만 JRebel을 실제로 동작시키려면 IDE 설정 외에도 실행 중 JVM에 맞는 Agent 설정 등이 필요합니다. 프로젝트 파일에 Nature가 있다는 사실만으로 재로딩이 활성화되는 것은 아닙니다.

| 항목 | 의미 |
| --- | --- |
| Eclipse 플러그인 | JRebel 설정과 실행을 IDE에서 지원 |
| JRebel Nature | 해당 프로젝트의 IDE 연동 설정 |
| `rebel.xml` | 변경된 클래스·리소스 위치 매핑 |
| 런타임 Agent | 실행 중 코드 재로딩을 수행하는 구성 요소 |

`rebel.xml`이 있다고 Agent가 붙어 있다는 뜻도 아니고, HCR이 동작한다고 JRebel이 실행 중이라는 뜻도 아닙니다. [DevTools·HCR·JRebel 비교](/blog/programming/devtools-hcr-jrebel)와 연결해서 보면 구분하기 쉽습니다.

## 쓰지 않는 설정이 왜 남아 있을까?

팀원이 JRebel을 쓰면서 공유한 프로젝트 설정이거나, 이전 개발 환경에서 만들어진 파일이 Git에 남아 있을 수 있습니다. 다른 IDE를 사용하다 Eclipse로 프로젝트를 가져올 때, 지금 설치되지 않은 플러그인의 흔적이 드러나기도 합니다.

이 경우 설정 파일의 존재만으로 플러그인을 모두 설치할 필요는 없습니다. 반대로 Maven 빌드가 성공했다는 이유만으로 Eclipse 설정을 전부 불필요하다고 판단할 수도 없습니다. 팀원이 여전히 사용하는 개발 기능일 수 있기 때문입니다.

## 정리하기 전에 확인할 순서

1. **현재 사용하는지 확인합니다.** 팀의 개발 안내와 실제 실행 구성을 살펴봅니다.
2. **역할을 나눠 봅니다.** IDE Nature, `rebel.xml`, JVM Agent 설정을 각각 확인합니다.
3. **Git 이력을 봅니다.** 언제 추가됐고 공유하려는 목적이 무엇이었는지 확인합니다.
4. **IDE의 설정 해제 기능을 먼저 검토합니다.** 플러그인이 설치되어 있다면 제공하는 프로젝트 설정에서 해제하는 편이 연관 설정을 파악하기 쉽습니다.
5. **수정 범위를 검토합니다.** Java·Maven Nature와 Builder, 필요한 클래스패스가 유지되는지 diff로 확인합니다.
6. **두 환경을 확인합니다.** Eclipse의 프로젝트 인식과 Maven 빌드를 각각 확인합니다.

`rebel.xml`을 공유할 때는 경로도 검토해야 합니다. 공식 안내에는 상대 경로를 활용하는 방법이 있으므로, 특정 개발자 PC의 절대 경로를 그대로 공유하는 것보다 이식성을 고려한 구성이 적합합니다.[2]

Nature는 프로젝트 기능의 설정이고, 재로딩은 실행 환경의 동작입니다. 이 두 층을 나누어 보면 “파일에 JRebel이라는 이름이 있으니 반드시 설치해야 하나?”라는 질문에 실제 사용 여부를 근거로 답할 수 있습니다.
