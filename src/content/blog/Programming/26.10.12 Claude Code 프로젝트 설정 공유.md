## 핵심 요약

- 프로젝트 공통 규칙과 절차를 저장소에 넣으면 로컬과 클라우드가 같은 자료를 사용할 수 있습니다.
- 파일이 전달된다는 것과 도구가 실제로 실행된다는 것은 다릅니다. 운영체제·의존성·인증·네트워크도 맞아야 합니다.
- 개인 설정, 인증 정보, 프로젝트에서 공유할 설정을 구분해서 관리해야 합니다.

## 웹에 다시 등록하기보다 저장소에서 관리하기

로컬에서 만든 검증 절차를 클라우드에서도 쓰고 싶다면, 우선 그 파일이 어디에 있는지 확인해야 합니다. 내 PC의 사용자 디렉터리에만 있는 파일은 저장소 clone에 포함되지 않습니다.

공식 문서는 프로젝트의 `CLAUDE.md`, Skills, Commands와 로컬 사용자 설정의 차이를 설명합니다. 단일 저장소 클라우드 세션에서 저장소의 설정·Hook과 `.mcp.json`을 읽는 경로도 안내합니다.[1]

| 용도 | 저장소 안의 위치 예시 | 공유 판단 |
| --- | --- | --- |
| 프로젝트 공통 지침 | `CLAUDE.md` | 공통 규칙을 작성 |
| 필요한 때 쓰는 작업 절차 | `.claude/skills/<name>/SKILL.md` | 빌드·검증·문서 절차 |
| 기존 Custom Command | `.claude/commands/<name>.md` | 기존 명령과 호환성 확인 |
| 프로젝트 설정·Hook | `.claude/settings.json` | 팀 공통 동작만 포함 |
| 프로젝트 MCP 정의 | `.mcp.json` | 비밀값 없는 정의만 공유 |
| 개인별 예외 | `.claude/settings.local.json` | 일반적으로 커밋하지 않음 |

여러 저장소가 함께 연결된 세션이나 조직 관리 환경은 적용 규칙이 달라질 수 있습니다. 모든 환경이 위 파일을 같은 우선순위로 적용한다고 가정하지는 않아야 합니다.

## Skill과 Custom Command를 어떻게 나눌까?

현재 공식 문서는 Custom Command가 Skills에 통합되었으며 기존 `.claude/commands/` 파일도 계속 지원된다고 설명합니다.[2] 새로 만드는 절차라면 Skill 디렉터리로 묶어 참고 자료와 보조 스크립트를 함께 관리하기 편합니다.

예를 들어 블로그에서 글을 검증하는 Skill은 다음처럼 작성할 수 있습니다. 아래 내용은 구조 예시이며, 해당 검사 스크립트가 실제로 존재하는 프로젝트에 맞게 조정해야 합니다.

```markdown
---
name: review-post
description: 블로그 글을 검토하고 콘텐츠 검사를 실행한다.
---

1. 수정한 글의 frontmatter와 공개 가능한 링크를 확인한다.
2. 프로젝트 루트에서 npm run check:content를 실행한다.
3. 검사 결과와 미확인 항목을 보고한다.
```

이 파일을 `.claude/skills/review-post/SKILL.md`에 두면 절차와 프로젝트 코드를 같은 변경 이력으로 관리할 수 있습니다. 반대로 개인적인 말투 선호나 다른 프로젝트에서도 쓰는 개인 절차를 모두 팀 저장소에 복사할 필요는 없습니다.

## 설정 파일도 공유 범위가 다르다

`.claude/settings.json`은 프로젝트 공통 설정에, `.claude/settings.local.json`은 개인별 예외에 사용할 수 있습니다.[3] 파일을 직접 만들었다면 로컬 설정이 Git에서 제외되는지도 확인해야 합니다.

또한 저장소에 선언한 플러그인이 클라우드에서 자동 설치된다고 가정하면 안 됩니다. 공식 환경 문서는 로컬 파일 전달과 플러그인 설치를 별개로 구분합니다.[1]

공유할 설정을 고를 때는 “내 PC에서 잘 됐다”보다 **새 clone에서도 같은 절차를 수행할 수 있는가**를 기준으로 보면 좋습니다.

## Hook은 경로와 실행 환경까지 확인하기

Hook은 특정 이벤트에 실제 명령을 실행합니다.[4] 문서 파일보다 운영체제와 실행 도구의 영향을 더 직접적으로 받습니다.

예를 들어 Windows 전용 명령을 호출하는 Hook을 Ubuntu 환경으로 가져오면 실행되지 않을 수 있습니다. Python이나 Node.js를 써도 런타임·패키지·실행 위치가 준비되어 있어야 하므로, 언어만 바꿨다고 완전히 이식 가능해지는 것은 아닙니다.

프로젝트 루트 기준의 경로를 사용하고, 필요한 의존성과 종료 코드를 명확히 정의하세요. 로컬과 원격에서 동작을 달리해야 한다면, 실행 환경을 구분하는 공식 변수와 환경 설정을 사용해 의도를 드러내는 편이 좋습니다.

## MCP 정의를 커밋하면 서버도 따라올까?

`.mcp.json`에는 서버 실행·연결 정의를 담을 수 있습니다.[5] 하지만 로컬 PC에서 실행 중인 서버 프로세스나 인증 상태가 파일 하나로 이동하지는 않습니다.

특히 클라우드에서 `localhost`는 보통 클라우드 실행 환경 자신을 가리킵니다. 내 PC의 로컬 DB나 MCP 서버를 의미하지 않습니다. 서버 실행 파일, 외부 주소의 도달 가능성, 필요한 인증을 각각 확인해야 합니다.

토큰을 JSON이나 Skill 본문에 그대로 넣기보다, 실행 환경이 제공하는 비밀값 주입·인증 방식을 사용해야 합니다. 저장소를 공유할 대상에게 공개해도 되는 내용인지도 함께 검토하세요.

## 적용하는 순서

1. **목록을 만듭니다.** 개인 설정과 프로젝트 전용 절차를 나눕니다.
2. **프로젝트 전용 파일부터 옮깁니다.** 빌드·테스트 명령처럼 재현 가능한 것부터 시작합니다.
3. **환경 의존성을 확인합니다.** 절대 경로, 운영체제 전용 명령, 런타임, 인증을 봅니다.
4. **Git diff를 검토합니다.** 토큰과 개인 경로, 관련 없는 설정이 포함되지 않았는지 확인합니다.
5. **새 환경에서 시험합니다.** 파일이 보이는지와 명령이 실제로 성공하는지를 따로 확인합니다.

이렇게 관리하면 CLI와 웹이 무조건 동일하게 동작한다고 기대하는 대신, 공통 절차와 환경별 차이를 분명히 남길 수 있습니다.
