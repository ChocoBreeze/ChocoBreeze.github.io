## 핵심 요약

- 여기서 바인딩은 다른 언어의 기능을 Java API로 사용할 수 있게 연결한 계층을 뜻합니다.
- Playwright Java는 기본적인 로컬 실행에서 별도 드라이버 프로세스를 띄우고 파이프로 통신합니다.
- Java API, 드라이버, 브라우저는 서로 다른 구성 요소이므로 설치와 문제 원인도 나누어 봐야 합니다.

## 같은 기능을 다른 언어에서 쓰게 하는 연결

“Playwright가 Java를 지원한다”는 말은 브라우저 자동화의 핵심 구현을 전부 Java로 다시 작성했다는 뜻은 아닙니다. Java 개발자가 `Page`, `Browser` 같은 객체를 통해 기능을 호출할 수 있도록 공식 API를 제공한다는 의미입니다.[1]

이처럼 다른 구현과 언어 사이를 연결한 API 계층을 **언어 바인딩(language binding)**이라고 부릅니다. 변수와 이름을 연결한다는 프로그래밍 언어의 다른 ‘바인딩’ 용례와는 문맥을 구분해야 합니다.

연결 방식은 하나가 아닙니다. JNI처럼 네이티브 코드를 호출할 수도 있고, 별도 프로세스와 메시지를 주고받을 수도 있습니다. 같은 인터페이스를 각 언어로 독립 구현한 라이브러리와도 구분할 필요가 있습니다.

## Playwright.create() 뒤에서 일어나는 일

Playwright Java의 기본 로컬 실행 경로를 소스에서 따라가면 흐름이 드러납니다. `PlaywrightImpl.createImpl()`은 드라이버 실행 명령에 `run-driver`를 추가하고 프로세스를 시작합니다. 이어서 그 프로세스의 입력·출력 스트림을 `PipeTransport`에 연결합니다.[2]

| 단계 | 수행하는 일 |
| --- | --- |
| Java 애플리케이션 | `Playwright.create()`로 실행 환경 생성 |
| Java 클라이언트 | 드라이버 프로세스 시작과 통신 연결 준비 |
| 드라이버 | Node.js에서 Playwright의 브라우저 제어 기능 수행 |
| 브라우저 | 페이지를 열고 실제 웹 동작 수행 |
| 응답 처리 | 결과를 Java API의 반환값이나 예외로 전달 |

`page.navigate(...)` 같은 호출은 이 통신 계층을 통해 전달됩니다. 로컬 객체처럼 보이는 `Page`도 브라우저 안의 페이지 그 자체는 아닙니다. 브라우저 쪽 대상을 다루는 Java API 객체라고 이해하면 좋습니다.

이 구조는 RMI나 RPC 클라이언트처럼 호출과 실제 실행 위치가 나뉜다는 점에서 비슷합니다. 다만 Playwright Java의 로컬 파이프 통신이 RMI 프로토콜을 사용한다는 뜻은 아닙니다.

## Node.js를 직접 설치해야 할까?

표준 배포 구성에서는 드라이버와 실행에 필요한 Node.js가 의존성 구성에 포함됩니다. 사용자가 별도로 Node.js를 설치하고 서버를 띄우는 절차가 기본 사용법은 아닙니다. 공식 저장소의 개발 안내도 드라이버를 Playwright Core 패키지와 대응하는 Node.js 바이너리로 조립한다고 설명합니다.[3]

하지만 **드라이버와 브라우저 바이너리는 별개**입니다. Playwright 버전에 맞는 브라우저를 준비해야 하며, 프로젝트에서는 CLI로 필요한 브라우저를 설치할 수 있습니다.[4]

```powershell
mvn exec:java '-Dexec.mainClass=com.microsoft.playwright.CLI' '-Dexec.args=install chromium'
```

이 명령은 Playwright Java 의존성이 설정된 Maven 프로젝트에서 실행하는 예시입니다. 사내 프록시나 제한된 네트워크에서는 브라우저 다운로드가 실패할 수 있으므로, Java 컴파일 실패와 다운로드 실패를 분리해서 확인해야 합니다.

## Java에서 호출하는 모습

Java에서는 JavaScript의 옵션 객체 대신 옵션 클래스를 사용하고, `try-with-resources`로 Playwright를 정리할 수 있습니다.[1]

```java
import com.microsoft.playwright.Browser;
import com.microsoft.playwright.BrowserType;
import com.microsoft.playwright.Playwright;

public class DriverDemo {
    public static void main(String[] args) {
        try (Playwright playwright = Playwright.create()) {
            Browser browser = playwright.chromium().launch(
                new BrowserType.LaunchOptions().setHeadless(true));
            try {
                System.out.println(browser.version());
            } finally {
                browser.close();
            }
        }
    }
}
```

겉으로는 동기 메서드 호출이지만, 내부에는 프로세스 간 요청과 응답이 있습니다. Java API가 이를 감싸므로 사용자가 매번 메시지 형식을 직접 만들 필요는 없습니다.

## 스레드 안전성과 오류 확인

공식 문서는 Playwright Java가 스레드 안전하지 않다고 설명합니다. 기본적으로 생성한 스레드에서 객체를 사용하거나, 동시에 하나의 스레드만 호출하도록 적절히 동기화해야 합니다.[5] 따라서 “어떤 경우에도 공유 불가”보다는 **동시 호출을 안전하게 보장하지 않는다**가 정확합니다.

병렬 테스트에서는 스레드별로 Playwright 인스턴스를 나누는 구성을 검토할 수 있습니다. 브라우저 컨텍스트를 분리하는 것만으로 Java 객체의 동시 접근 문제가 해결되지는 않습니다.

실행 문제가 생기면 다음처럼 범위를 나누면 좋습니다.

- Java 컴파일 단계의 오류인지, 드라이버 프로세스를 시작하지 못한 것인지 확인합니다.
- 브라우저 설치·실행 문제인지, 실제 페이지의 선택자·대기 조건 문제인지 구분합니다.
- Java 의존성과 설치한 브라우저의 버전 대응을 확인합니다.

언어마다 API 형태와 테스트 러너가 다르므로, 같은 Playwright 계열을 사용한다고 모든 언어의 동작과 주변 기능이 완전히 같다고 가정해서는 안 됩니다. Java API와 공통 브라우저 제어 계층의 역할을 나누면 문서를 읽고 오류를 추적하기 쉬워집니다.
