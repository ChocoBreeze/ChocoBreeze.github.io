## 핵심 요약

- Quality Gate는 소프트웨어가 다음 단계로 진행하기 위해 충족해야 하는 품질 기준입니다.
- 검사를 실행하는 것, 결과를 통과·실패로 판정하는 것, 실패 시 진행을 막는 것은 각각 연결해야 합니다.
- `SW Quality Gate & Lifecycle 구축`은 단일 표준 기술명보다는 품질 검증과 개발 생명주기 관리를 함께 다루는 과제명으로 이해할 수 있습니다.

## 테스트를 돌리면 Quality Gate가 생길까?

PR마다 테스트를 실행하고 결과를 댓글로 남긴다고 가정해 보겠습니다. 실패한 PR도 그대로 병합할 수 있다면, 결과를 알려주는 기능은 있지만 병합을 통제하는 장치는 부족합니다.

Quality Gate를 구축하려면 다음 세 가지를 연결해야 합니다.

| 구성 | 예 |
| --- | --- |
| 기준 | 필수 테스트 성공, 새 코드 커버리지 목표, 특정 심각도의 문제 없음 |
| 판정 | CI나 분석 도구가 기준 충족 여부를 결과로 보고 |
| 강제 적용 | 필수 검사 실패 시 PR 병합 또는 배포 진행 차단 |

“품질 검사를 추가했다”와 “품질 기준을 충족해야 병합된다”는 서로 다른 구현 결과입니다.

## 어떤 기준을 둘 수 있을까?

프로젝트의 위험과 유지 비용에 맞춰 선택합니다. 아래는 **설계 예시이며 모든 조직에 적용되는 표준 수치는 아닙니다.**

| 영역 | 기준 예시 | 함께 볼 점 |
| --- | --- | --- |
| 빌드 | 배포 산출물 생성 성공 | 개발 모드 실행 성공만으로 대신하지 않기 |
| 테스트 | 필수 단위·통합 테스트 통과 | 실제로 실행되었는지 확인 |
| 커버리지 | 새 코드의 커버리지 80% 이상 | 테스트가 업무 동작을 검증하는지 |
| 정적 분석 | 지정한 심각도 이상의 새 문제 없음 | 오탐 검토와 예외 승인 절차 |
| 의존성 검사 | 정책상 차단할 취약점 없음 | 공지 갱신과 수정 버전 확인 |

커버리지 숫자가 높다고 테스트의 품질까지 보장되지는 않습니다. 반대로 기존 코드 전체에 높은 목표를 즉시 적용하면 작은 개선도 진행하지 못할 수 있습니다. 새 코드와 기존 코드의 기준을 나누고 단계적으로 적용하는 방법을 검토할 수 있습니다.

## SonarQube는 무엇을 맡을까?

SonarQube의 Quality Gate는 코드 분석 결과에 조건을 적용해 통과·실패를 판정합니다. 조건은 새 코드 또는 전체 코드의 지표에 적용될 수 있으며, PR에서는 새 코드에 적용되는 조건을 평가합니다.[1]

PR 분석 결과를 GitHub에 표시하더라도, 실제 병합 차단까지 구성했는지는 별도로 확인해야 합니다. 사용하는 SonarQube 제품·에디션·버전의 PR 분석과 저장소 연동 지원 범위도 확인할 필요가 있습니다.

SonarQube만으로 모든 빌드·테스트·취약점 검사 정책을 자동으로 구성해 주는 것은 아닙니다. 분석 도구의 판정과 별도 CI 작업의 결과를 함께 필수 조건으로 사용할 수 있습니다.

## GitHub에서 병합을 막는 연결

일반적인 구성 순서는 다음과 같습니다.

1. PR의 변경 내용을 대상으로 CI와 코드 분석을 실행합니다.
2. 실패하면 해당 작업이 실패 상태를 보고하도록 구성합니다.
3. 보호 브랜치 규칙이나 ruleset에서 해당 상태 검사를 필수로 지정합니다.
4. 의도적으로 실패하는 변경을 만들어 실제로 병합이 차단되는지 확인합니다.

GitHub의 required status checks는 보호 브랜치에 변경을 넣기 전에 지정한 검사가 충족되어야 하도록 설정합니다.[2] 검사 이름의 충돌, 관리자 우회 권한, 필수 워크플로가 건너뛰어지는 경우도 정책의 실제 동작에 영향을 줍니다.

분석 명령이 실패해도 `continue-on-error` 등으로 최종 작업을 성공 처리하면 원하는 차단 결과가 전달되지 않을 수 있습니다. 도구 화면의 빨간 표시와 GitHub가 받는 상태가 일치하는지 확인하는 것이 필요합니다.

## Lifecycle에는 어디에 배치할까?

여기서 Lifecycle은 소프트웨어의 기획·개발·테스트·배포·운영·유지보수에 이르는 SDLC를 가리킨다고 정의하면 명확해집니다. 아래는 단계별 정책의 한 예입니다.

| 시점 | 확인할 것 | 다음 단계의 조건 |
| --- | --- | --- |
| 로컬 개발 | 빠른 포맷·단위 검사 | 개발 피드백 |
| PR | 리뷰, 빌드, 테스트, 정적 분석 | 병합 승인과 필수 검사 |
| 릴리스 | 패키징, 통합 검증, 배포 준비 | 배포 승인 |
| 운영 | 오류율·지연·상태 모니터링 | 배포 유지 또는 롤백 판단 |

모든 검사를 매번 같은 위치에서 반복하는 것이 목표는 아닙니다. 빠른 검사는 앞에 배치하고, 비용이 큰 검사는 위험에 맞는 단계에 배치해 피드백 시간을 관리합니다.

## 도구 설치 다음에 남는 일

게이트가 자주 실패한다면 실패 원인을 구분해야 합니다. 실제 결함, 불안정한 테스트, 외부 서비스 장애, 갱신된 취약점 공지는 대응이 다릅니다.

특히 며칠 전 통과한 CI가 오늘도 같은 의존성 보안 상태를 보장하지는 않습니다. 중요 작업 전 재검사나 정기 검사를 어디에 둘지도 정책의 일부입니다.

실무에서는 기준의 담당자, 예외를 승인할 권한과 만료 시점, 실패를 해결하는 절차를 함께 정해야 합니다. “모든 경고를 무조건 차단”보다는 어떤 위험을 어느 단계에서 막을지 명확히 정하는 것이 운영하기 쉽습니다.

과제명으로는 **SW 품질 게이트 및 개발 생명주기 관리 체계 구축**처럼 관리 대상을 드러낼 수 있습니다. 자동화가 중심이라면 “Quality Gate 및 CI/CD 체계 구축”으로 범위를 좁히는 것도 방법입니다.
