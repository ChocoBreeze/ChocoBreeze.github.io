개발하다 보면 서로 다른 언어로 작성된 프로그램이 통신해야 하는 상황을 자주 만나게 됩니다.

예를 들어 서버는 Java로 작성되어 있고, 일부 고성능 모듈은 C++로 구현되어 있으며, 클라이언트는 Python이나 JavaScript를 사용할 수 있습니다. 이때 한 언어에서 정의한 함수나 객체를 다른 언어가 그대로 이해할 수는 없습니다.

C++에서 다음과 같은 함수를 정의했다고 생각해보겠습니다.

```cpp
User getUser(int id);
```

C++ 컴파일러는 이 함수의 이름, 매개변수 타입, 반환 타입을 이해합니다. 하지만 Java나 Python 프로그램은 이 C++ 선언만 보고 함수의 호출 방법을 알 수 없습니다.

서로 다른 언어와 시스템이 통신하려면 다음과 같은 내용을 공통된 형식으로 약속해야 합니다.

* 어떤 기능을 제공하는가?
* 기능의 이름은 무엇인가?
* 어떤 데이터를 입력받는가?
* 어떤 데이터를 반환하는가?
* 데이터는 어떤 구조를 가지는가?
* 오류는 어떻게 표현되는가?

이러한 인터페이스 계약을 언어에 독립적인 방식으로 표현하기 위해 사용하는 것이 **IDL**입니다.

---

## IDL이란?

IDL은 **Interface Definition Language**의 약자로, 한국어로는 보통 **인터페이스 정의 언어**라고 부릅니다.

IDL은 프로그램의 실제 동작을 구현하는 언어가 아닙니다. 서로 다른 프로그램이 어떤 방식으로 데이터를 주고받을지를 정의하는 명세 언어입니다.

쉽게 표현하면 다음과 같습니다.

> IDL은 서로 다른 프로그램과 언어가 통신하기 위해 사용하는 공통 인터페이스 설계도다.

일반적인 프로그래밍 언어에서는 함수의 내부 동작을 작성합니다.

```cpp
User getUser(int id) {
    return database.findUser(id);
}
```

반면 IDL에서는 함수가 존재한다는 사실과 입출력 구조만 정의합니다.

```text
GetUser
입력: 사용자 ID
출력: 사용자 정보
```

사용자를 데이터베이스에서 어떻게 조회할지, 캐시를 사용할지, 오류를 어떻게 복구할지와 같은 실제 구현은 IDL에 포함되지 않습니다.

IDL은 오직 **외부에서 보이는 계약**을 정의합니다.

---

## IDL은 왜 필요한가?

IDL이 해결하려는 핵심 문제는 **언어와 플랫폼의 차이**입니다.

C++에서는 다음과 같이 인터페이스를 선언할 수 있습니다.

```cpp
class UserService {
public:
    User getUser(int id);
};
```

Java에서는 비슷한 인터페이스를 다음과 같이 표현합니다.

```java
public interface UserService {
    User getUser(int id);
}
```

Python에서는 문법이 또 다릅니다.

```python
class UserService:
    def get_user(self, user_id: int):
        pass
```

세 코드는 개념적으로 같은 기능을 나타내지만, 문법과 타입 시스템은 서로 다릅니다.

여기에 네트워크 통신까지 포함되면 문제는 더 복잡해집니다. 다른 컴퓨터에 있는 함수는 일반적인 함수 호출처럼 직접 실행할 수 없기 때문입니다.

```text
클라이언트 프로그램
        ↓
네트워크
        ↓
서버 프로그램
```

클라이언트와 서버는 다음 사항을 정확히 공유해야 합니다.

```text
메서드 이름
입력 메시지 구조
출력 메시지 구조
데이터 타입
직렬화 방식
오류 형식
```

이 계약을 각 언어에서 따로 작성하면 중복이 발생하고, 한쪽 코드만 수정되어 클라이언트와 서버의 규격이 달라질 수도 있습니다.

IDL을 사용하면 하나의 명세를 기준으로 여러 언어의 코드를 생성할 수 있습니다.

```text
             IDL
              │
      ┌───────┼───────┐
      ▼       ▼       ▼
   Java 코드 C++ 코드 Python 코드
```

즉, IDL은 여러 시스템 사이에서 **하나의 공통 진실 공급원** 역할을 합니다.

---

## C++의 헤더 파일과 비슷한가?

C++ 경험이 있다면 IDL을 **언어 중립적인 헤더 파일**처럼 생각할 수 있습니다.

C++ 헤더 파일에는 클래스, 함수, 매개변수, 반환 타입 등이 선언됩니다.

```cpp
class UserService {
public:
    User getUser(int id);
};
```

이 선언만 보면 함수를 사용하는 방법은 알 수 있지만, 함수가 내부적으로 어떻게 구현되어 있는지는 알 수 없습니다.

IDL도 비슷한 역할을 합니다.

다만 중요한 차이가 있습니다.

C++ 헤더 파일은 기본적으로 C++ 컴파일러를 위한 선언입니다. 반면 IDL은 Java, C++, Python, Go 등 여러 언어가 공유할 수 있는 중립적인 명세입니다.

또한 IDL은 네트워크를 통한 원격 호출을 위해 사용되는 경우가 많습니다. 따라서 단순한 함수 선언뿐 아니라 메시지 직렬화와 통신 코드 생성에도 관여합니다.

---

## 대표적인 IDL: Protocol Buffers

현재 IDL을 접할 가능성이 높은 대표적인 기술은 **gRPC와 Protocol Buffers**입니다.

gRPC에서는 일반적으로 `.proto` 파일에 서비스와 메시지를 정의합니다.

```proto
syntax = "proto3";

service UserService {
  rpc GetUser(GetUserRequest)
      returns (UserResponse);
}

message GetUserRequest {
  int32 id = 1;
}

message UserResponse {
  string name = 1;
  int32 age = 2;
}
```

이 파일에는 두 종류의 정보가 들어 있습니다.

첫 번째는 서비스 인터페이스입니다.

```proto
service UserService {
  rpc GetUser(GetUserRequest)
      returns (UserResponse);
}
```

`UserService`라는 서비스가 있고, 그 안에 `GetUser`라는 원격 호출 메서드가 있다는 의미입니다.

`GetUser`는 `GetUserRequest` 메시지를 입력받아 `UserResponse` 메시지를 반환합니다.

두 번째는 통신에 사용할 데이터 구조입니다.

```proto
message GetUserRequest {
  int32 id = 1;
}
```

이 메시지는 정수형 사용자 ID를 포함합니다.

```proto
message UserResponse {
  string name = 1;
  int32 age = 2;
}
```

응답 메시지는 사용자의 이름과 나이를 포함합니다.

여기에서도 사용자를 데이터베이스에서 어떻게 찾는지는 정의하지 않습니다. 외부에서 요청과 응답이 어떤 형태로 보이는지만 정의합니다.

---

## IDL에서 코드가 생성되는 과정

`.proto`와 같은 IDL 파일을 작성한 다음에는 코드 생성기를 실행합니다.

Protocol Buffers에서는 일반적으로 `protoc`이라는 컴파일러를 사용합니다.

```text
user.proto
    │
    ▼
Protocol Buffers 컴파일러
    │
    ├── Java 코드
    ├── C++ 코드
    ├── Python 코드
    └── Go 코드
```

여기서 생성되는 코드는 단순한 데이터 클래스만이 아닙니다. 사용하는 프레임워크에 따라 다음 코드들이 함께 생성될 수 있습니다.

* 요청 및 응답 메시지 클래스
* 직렬화와 역직렬화 코드
* 클라이언트용 Stub
* 서버가 구현할 기본 클래스
* 메서드 호출에 필요한 통신 코드

개발자는 네트워크 통신의 세부 구현을 처음부터 모두 작성하지 않아도 됩니다.

Java 서버라면 생성된 서버 인터페이스를 구현합니다.

```java
public class UserServiceImpl
        extends UserServiceGrpc.UserServiceImplBase {

    @Override
    public void getUser(
            GetUserRequest request,
            StreamObserver<UserResponse> responseObserver) {

        UserResponse response = UserResponse.newBuilder()
                .setName("Younghoon")
                .setAge(25)
                .build();

        responseObserver.onNext(response);
        responseObserver.onCompleted();
    }
}
```

Python 클라이언트에서는 생성된 Stub을 통해 메서드를 호출할 수 있습니다.

```python
request = GetUserRequest(id=1)
response = stub.GetUser(request)

print(response.name)
```

코드만 보면 일반적인 객체의 메서드를 호출하는 것처럼 보입니다.

그러나 실제로는 네트워크 요청과 응답이 발생합니다.

---

## Stub이란?

IDL과 RPC를 공부할 때 자주 등장하는 개념이 **Stub**입니다.

Stub은 원격 서버의 기능을 로컬 함수처럼 호출할 수 있도록 감싸주는 클라이언트 측 대리 객체입니다.

예를 들어 다음 코드가 있다고 가정해보겠습니다.

```python
response = stub.GetUser(request)
```

겉으로 보면 Python 객체의 `GetUser` 메서드를 호출하는 것처럼 보입니다.

하지만 Stub 내부에서는 다음 작업이 수행됩니다.

```text
GetUser 호출
    ↓
요청 객체 직렬화
    ↓
네트워크를 통해 서버로 전송
    ↓
서버가 요청 처리
    ↓
응답 데이터 수신
    ↓
응답 객체로 역직렬화
```

Stub은 이러한 복잡한 작업을 감추고 개발자에게 익숙한 함수 호출 형태를 제공합니다.

C++ 관점에서는 Stub을 특정 인터페이스를 구현하는 **프록시 객체**와 비슷하게 볼 수 있습니다.

다만 실제 함수가 같은 프로세스 안에서 실행되는 것이 아니라, Stub 뒤에서 네트워크 통신이 발생한다는 차이가 있습니다.

---

## 직렬화와 역직렬화

네트워크에서는 Java 객체나 C++ 객체를 메모리 상태 그대로 보낼 수 없습니다.

예를 들어 다음 Java 객체가 있다고 하겠습니다.

```java
User user = new User("Younghoon", 25);
```

이 객체는 JVM 내부 메모리에 존재합니다. C++ 서버는 JVM의 객체 구조를 알지 못하므로 이 객체를 그대로 읽을 수 없습니다.

따라서 객체를 전송 가능한 데이터 형식으로 변환해야 합니다.

이 과정을 **직렬화(Serialization)**라고 합니다.

```text
User 객체
    ↓ 직렬화
바이트 데이터
```

수신 측에서는 바이트 데이터를 다시 자신이 사용하는 언어의 객체로 복원합니다.

이 과정을 **역직렬화(Deserialization)**라고 합니다.

```text
바이트 데이터
    ↓ 역직렬화
User 객체
```

Protocol Buffers는 IDL에 정의된 메시지 구조를 바탕으로 각 언어에 맞는 직렬화와 역직렬화 코드를 자동 생성합니다.

그래서 Java에서 만든 요청을 C++ 서버가 읽고, C++ 서버가 만든 응답을 Python 클라이언트가 읽을 수 있습니다.

## 원격 함수 호출의 실제 흐름

클라이언트에서 다음 코드를 실행했다고 생각해보겠습니다.

```java
UserResponse response = client.getUser(1);
```

개발자에게는 단순한 메서드 호출처럼 보이지만, 내부에서는 대략 다음 과정이 발생합니다.

```text
1. 클라이언트가 getUser() 호출
2. Stub이 요청 메시지 생성
3. 요청 메시지를 바이트로 직렬화
4. 네트워크를 통해 서버에 전송
5. 서버가 바이트를 요청 객체로 역직렬화
6. 서버의 실제 getUser() 구현 실행
7. 서버가 응답 객체 생성
8. 응답을 바이트로 직렬화
9. 네트워크를 통해 클라이언트에 전송
10. 클라이언트가 응답 객체로 역직렬화
```

즉, 다음 두 코드는 겉모습은 비슷하지만 실행 구조가 완전히 다릅니다.

일반 함수 호출:

```text
호출자 → 같은 프로세스의 함수
```

RPC 호출:

```text
호출자 → Stub → 네트워크 → 서버 → 실제 함수
```

IDL은 이 과정에서 클라이언트와 서버가 동일한 요청 및 응답 구조를 사용하도록 보장하는 기준이 됩니다.

## IDL과 API는 무엇이 다른가?

IDL과 API는 비슷하게 들리지만 같은 개념은 아닙니다.

**API(Application Programming Interface)**는 프로그램이 외부에 제공하는 기능과 사용 방법을 의미합니다.

예를 들어 다음 Java 메서드는 API의 일부가 될 수 있습니다.

```java
User getUser(int id);
```

IDL은 이러한 API의 인터페이스 구조를 언어 중립적으로 작성한 명세입니다.

```proto
rpc GetUser(GetUserRequest)
    returns (UserResponse);
```

관계를 정리하면 다음과 같습니다.

```text
IDL
 ↓ 코드 생성
언어별 인터페이스와 통신 코드
 ↓ 구현
실제 API 서비스
```

IDL은 API 자체라기보다는 **API를 정의하고 생성하기 위한 원본 계약**에 가깝습니다.

---

## IDL과 OpenAPI는 같은 것인가?

OpenAPI도 API의 입출력과 경로를 명세한다는 점에서 IDL과 비슷한 역할을 합니다.

예를 들어 REST API는 다음과 같이 정의할 수 있습니다.

```yaml
paths:
  /users/{id}:
    get:
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
```

이 명세를 기반으로 문서를 만들거나 클라이언트 코드를 생성할 수 있습니다.

다만 일반적으로 두 기술의 중심 목적에는 차이가 있습니다.

Protocol Buffers 같은 전통적인 IDL은 RPC 메서드와 바이너리 메시지 구조를 정의하는 데 초점이 있습니다.

OpenAPI는 HTTP 기반 REST API의 URL, HTTP 메서드, 요청, 응답, 상태 코드 등을 정의하는 데 초점이 있습니다.

```text
Protocol Buffers
- 서비스와 RPC 메서드 중심
- 바이너리 직렬화
- 강한 타입 계약
- gRPC에서 주로 사용

OpenAPI
- URL과 HTTP 메서드 중심
- JSON 기반 REST API에서 주로 사용
- API 문서 및 테스트 도구와 연결하기 쉬움
```

둘은 형식과 생태계가 다르지만, 시스템 간 인터페이스 계약을 기계가 읽을 수 있는 형식으로 작성한다는 공통점이 있습니다.

## MCP의 Tool Schema도 IDL인가?

MCP에서는 Tool을 다음과 비슷한 형태로 정의합니다.

```json
{
  "name": "search_user",
  "description": "사용자 ID로 사용자를 조회합니다.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "id": {
        "type": "integer"
      }
    },
    "required": ["id"]
  }
}
```

이 정의에는 다음 정보가 들어 있습니다.

* Tool의 이름
* Tool이 하는 일
* 입력 데이터의 구조
* 필수 입력값
* 각 필드의 데이터 타입

역할만 보면 IDL과 상당히 비슷합니다. 호출 가능한 기능과 입력 계약을 기계가 이해할 수 있는 형태로 정의하기 때문입니다.

다만 MCP가 `.proto`와 같은 전용 IDL을 사용하는 것은 아닙니다. MCP의 Tool 입력은 주로 JSON Schema를 사용해 표현됩니다.

따라서 다음과 같이 구분할 수 있습니다.

```text
gRPC
.proto라는 전용 IDL로 서비스와 메시지를 정의

MCP
JSON Schema로 Tool의 입력 인터페이스를 정의
```

MCP의 Tool Schema를 전통적인 IDL과 완전히 동일하다고 부르기보다는, **IDL과 유사한 인터페이스 명세 역할을 수행한다**고 이해하는 편이 정확합니다.

---

## IDL을 사용하면 얻을 수 있는 장점

IDL의 가장 큰 장점은 클라이언트와 서버 사이의 계약을 코드로 관리할 수 있다는 점입니다.

### 언어 독립성

하나의 IDL을 기준으로 Java, C++, Python, Go 등 여러 언어의 코드를 생성할 수 있습니다.

### 반복 코드 감소

요청 및 응답 클래스, 직렬화 코드, Stub 등을 직접 작성하지 않아도 됩니다.

### 타입 안정성

서버가 정수를 기대하는데 클라이언트가 문자열을 보내는 것과 같은 오류를 개발 단계에서 발견하기 쉬워집니다.

### 계약의 일관성

클라이언트와 서버가 서로 다른 문서를 참고하는 대신 동일한 IDL 파일을 기준으로 개발할 수 있습니다.

### 자동화

IDL을 기준으로 코드 생성, 문서화, 테스트, 호환성 검사 등을 자동화할 수 있습니다.

---

## IDL이 모든 문제를 해결해주는 것은 아니다

IDL이 있다고 해서 분산 시스템의 복잡성이 사라지는 것은 아닙니다.

코드에서는 원격 호출도 일반 함수 호출처럼 보일 수 있습니다.

```java
UserResponse response = client.getUser(request);
```

하지만 실제로는 네트워크를 사용하므로 다음 문제가 발생할 수 있습니다.

* 서버가 응답하지 않을 수 있음
* 네트워크가 끊길 수 있음
* 응답이 늦어질 수 있음
* 요청이 중복으로 전달될 수 있음
* 클라이언트와 서버의 IDL 버전이 다를 수 있음
* 일부 요청만 성공하고 나머지는 실패할 수 있음

일반적인 로컬 함수 호출에서는 함수가 반환되거나 예외를 던지는 정도를 생각하면 됩니다.

하지만 원격 호출에서는 타임아웃, 재시도, 네트워크 장애, 부분 실패까지 고려해야 합니다.

따라서 Stub이 로컬 객체처럼 보인다고 해서 실제로도 로컬 호출처럼 동작한다고 생각하면 안 됩니다.

> RPC는 함수 호출처럼 보이게 만든 네트워크 통신이다.

이 점이 IDL과 RPC를 이해할 때 가장 중요한 부분 중 하나입니다.

---

## IDL을 변경할 때 주의할 점

IDL은 클라이언트와 서버가 공유하는 계약이므로 변경할 때 호환성을 고려해야 합니다.

Protocol Buffers 메시지를 예로 들어보겠습니다.

```proto
message UserResponse {
  string name = 1;
  int32 age = 2;
}
```

여기서 `= 1`, `= 2`는 단순한 필드 순서가 아니라 데이터를 바이너리로 구분하기 위한 **필드 번호**입니다.

이미 사용하던 필드 번호를 다른 의미로 재사용하면 이전 버전의 프로그램이 데이터를 잘못 해석할 수 있습니다.

예를 들어 기존 `age = 2`를 삭제한 뒤 같은 번호를 `email`에 사용하면 위험합니다.

```proto
message UserResponse {
  string name = 1;
  string email = 2;
}
```

이전 클라이언트는 필드 번호 2를 여전히 나이로 해석하려고 할 수 있습니다.

따라서 사용이 중단된 필드 번호는 보통 `reserved`로 남겨둡니다.

```proto
message UserResponse {
  reserved 2;

  string name = 1;
  string email = 3;
}
```

IDL은 단순한 코드 생성 파일이 아니라 여러 시스템이 공유하는 장기적인 계약입니다. 그래서 파일을 수정할 때도 일반 구현 코드보다 호환성을 더 신중하게 고려해야 합니다.

---

## 대표적으로 IDL을 사용하는 기술

IDL은 특정 제품 하나의 이름이 아니라 인터페이스 정의 방식에 대한 일반적인 개념입니다.

대표적인 기술은 다음과 같습니다.

| 기술            | 인터페이스 정의 형식      | 주요 용도              |
| ------------- | ---------------- | ------------------ |
| gRPC          | Protocol Buffers | 고성능 RPC 통신         |
| Apache Thrift | Thrift IDL       | 다중 언어 RPC          |
| CORBA         | CORBA IDL        | 분산 객체 통신           |
| Microsoft COM | MIDL             | Windows 컴포넌트 인터페이스 |
| Apache Avro   | Avro Schema      | 데이터 직렬화 및 메시징      |
| Cap'n Proto   | Schema Language  | 빠른 직렬화 및 RPC       |
| OpenAPI       | YAML 또는 JSON     | HTTP REST API 명세   |

구체적인 문법은 다르지만 핵심 목적은 비슷합니다.

> 프로그램이 제공하는 기능과 데이터 구조를 구현 언어와 분리하여 명시적인 계약으로 정의한다.

---

## 전체 구조 정리

IDL이 사용되는 전체 과정을 정리하면 다음과 같습니다.

```text
1. 개발자가 IDL에 서비스와 메시지를 정의한다.

2. 코드 생성기가 IDL을 읽는다.

3. 각 프로그래밍 언어에 맞는 코드를 생성한다.

4. 서버 개발자는 생성된 인터페이스의 실제 동작을 구현한다.

5. 클라이언트는 생성된 Stub을 통해 서버를 호출한다.

6. Stub과 서버 코드가 직렬화, 역직렬화, 네트워크 통신을 처리한다.
```

각 구성 요소의 역할은 다음과 같습니다.

```text
IDL
클라이언트와 서버가 공유하는 계약

코드 생성기
IDL을 각 언어의 코드로 변환

Stub
클라이언트 측에서 원격 기능을 로컬 메서드처럼 제공

서버 구현체
실제 비즈니스 로직을 실행

직렬화 코드
객체와 전송용 바이트 사이를 변환

네트워크 계층
클라이언트와 서버 사이에서 데이터를 전달
```

---

## 마무리

IDL은 서로 다른 언어와 프로그램이 통신하기 위해 사용하는 **인터페이스 계약을 정의하는 언어**입니다.

IDL 자체에는 실제 비즈니스 로직이 들어가지 않습니다. 대신 서비스의 이름, 메서드, 입력 데이터, 출력 데이터와 같은 외부 계약을 정의합니다.

이 명세를 기반으로 각 언어의 메시지 클래스, Stub, 서버 인터페이스, 직렬화 코드가 자동 생성됩니다.

핵심을 한 문장으로 정리하면 다음과 같습니다.

> IDL은 서로 다른 언어와 시스템이 같은 규격으로 통신할 수 있도록 만드는 언어 중립적인 인터페이스 설계도다.

그리고 IDL을 이해할 때는 다음 흐름을 함께 기억하는 것이 좋습니다.

```text
IDL 작성
    ↓
언어별 코드 생성
    ↓
Stub을 통한 메서드 호출
    ↓
요청 직렬화
    ↓
네트워크 전송
    ↓
서버 구현 실행
    ↓
응답 역직렬화
```

IDL은 단순히 문법 하나를 배우는 주제가 아닙니다. RPC, gRPC, 직렬화, API 계약, 코드 생성, 분산 시스템의 버전 호환성을 연결해주는 출발점입니다.
