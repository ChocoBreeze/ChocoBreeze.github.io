## 핵심 요약

- 모델은 다음 행동을 제안하고, 실행 프로그램은 도구 호출을 받아 실제 브라우저를 움직입니다.
- 하네스는 실행 흐름을 관리하고, MCP 서버는 도구를 제공하며, Playwright 같은 라이브러리는 브라우저 조작을 수행합니다.
- 화면이 바뀌었다는 사실과 원하는 기능이 정상 동작한다는 사실은 다르므로, 작업에 맞는 검증이 필요합니다.

## 모델의 판단이 실제 클릭으로 바뀌기까지

AI에게 “페이지를 열고 저장 버튼이 동작하는지 확인해 줘”라고 요청했다고 가정해 보겠습니다. 모델의 추론만으로 운영체제에 클릭이 전달되지는 않습니다. 모델이 선택한 동작을 실제 프로그램이 실행해야 합니다.

예를 들어 실행 환경이 `browser_click`이라는 도구와 입력 형식을 제공하면, 모델은 클릭 대상 등의 인자를 담은 호출을 생성합니다. 이 호출을 받아 처리하는 프로그램이 브라우저를 조작하고 결과를 돌려줍니다. 아래 JSON은 개념을 설명하기 위한 예시이며, 특정 제품의 실제 API 형식은 아닙니다.

```json
{
  "tool": "browser_click",
  "arguments": {
    "element": "저장 버튼",
    "ref": "button-12"
  }
}
```

실행 결과가 다시 입력으로 들어오면 모델은 “저장 완료 안내가 나타났는가?”, “오류를 더 확인해야 하는가?”를 판단합니다. 이처럼 **관찰 → 행동 선택 → 실행 → 재관찰**을 반복하는 구조입니다. 실제로 사용할 수 있는 행동은 연결된 도구와 권한에 따라 달라집니다.

## 하네스와 MCP 서버는 같은 것일까?

두 역할을 나누면 구조를 이해하기 쉽습니다. MCP는 AI 애플리케이션과 외부 도구를 연결하는 프로토콜이며, 호스트·클라이언트·서버 구조를 사용합니다.[1]

| 구성 요소 | 맡는 일 | 예시 |
| --- | --- | --- |
| 모델 | 관찰 결과를 해석하고 다음 행동 선택 | 저장 버튼 클릭을 요청 |
| 하네스·호스트 애플리케이션 | 모델 호출, 도구 실행 전달, 상태와 권한 관리 | 코딩 에이전트의 실행 환경 |
| MCP 클라이언트 | 호스트에서 MCP 서버와 통신 | 서버의 도구 목록 조회와 호출 |
| MCP 서버 | 정해진 형식으로 도구 제공 | Playwright MCP 서버 |
| 자동화 라이브러리 | 페이지 이동, 입력, 클릭 등을 구현 | Playwright |
| 브라우저 | 페이지와 JavaScript 실행 | Chromium, Firefox, WebKit |

MCP 서버가 모든 판단과 반복 실행을 담당하는 것은 아닙니다. 또한 브라우저 자동화에 MCP가 반드시 필요한 것도 아닙니다. 애플리케이션이 자동화 라이브러리를 직접 호출하는 방식도 가능합니다.

## 브라우저와 연결되는 방법

Chrome DevTools Protocol(CDP)은 Chrome 계열 브라우저의 디버깅·제어 인터페이스입니다. 페이지나 네트워크 상태를 관찰하고 제어하는 기능을 제공합니다.[2]

Playwright와 Puppeteer는 이런 저수준 통신을 직접 다루는 수고를 줄여 주는 자동화 라이브러리입니다. 다만 **두 도구의 모든 브라우저 제어가 CDP로 이루어지는 것은 아닙니다.** Playwright는 Chromium뿐 아니라 Firefox와 WebKit을 지원하고, Puppeteer도 WebDriver BiDi를 통해 Firefox를 지원합니다.[3][4]

브라우저 확장 프로그램을 통해 사용 중인 탭과 연결하는 제품도 있습니다. 이때 기존 로그인 상태를 이용할 수 있는지는 해당 도구의 연결 방식에 달려 있습니다.

## 무엇을 보고 정상 동작을 판단할까?

Playwright MCP는 접근성 정보를 담은 구조화된 스냅샷을 주요 상호작용 수단으로 제공합니다.[5] 스크린샷과 스냅샷은 서로 다른 정보를 줍니다.

| 관찰 결과 | 확인하기 좋은 것 | 그것만으로 부족한 것 |
| --- | --- | --- |
| 스크린샷 | 배치, 겹침, 잘림, 오류 화면 | 데이터가 실제로 저장됐는지 |
| 접근성 스냅샷·DOM | 요소 이름, 역할, 상태 | 시각적인 깨짐 전체 |
| 콘솔 로그 | JavaScript 오류와 경고 | 사용자의 최종 작업 성공 여부 |
| 네트워크 응답 | 요청 결과와 응답 내용 | 올바른 업무 결과인지 |
| 명시적인 단언 | 예상한 텍스트·상태와 실제 결과 비교 | 단언하지 않은 다른 동작 |

저장 기능이라면 버튼 클릭 후 완료 문구만 확인할 수도 있지만, 더 강한 검증은 새로고침 후에도 수정한 값이 유지되는지 보는 것입니다. 필요한 관찰은 검증하려는 목표에서 정해야 합니다.

## 자동화할 때 남는 한계

좌표 클릭은 창 크기나 스크롤 위치가 달라지면 대상이 바뀔 수 있습니다. 요소의 역할·이름이나 스냅샷 참조로 대상을 식별하면 이런 문제를 줄일 수 있지만, 잘못된 대상을 선택할 가능성까지 없어지지는 않습니다.

웹페이지에 적힌 문장은 외부 데이터입니다. 페이지 안의 문구가 에이전트에게 다른 행동을 요구하더라도, 그것이 사용자가 내린 지시와 같은 권한을 갖는 것은 아닙니다. Playwright MCP 자체도 보안 경계가 아니므로, 호스트의 권한 정책과 실행 환경의 격리가 별도로 필요합니다.[5]

같은 시나리오를 반복 확인할 때는 탐색 과정에서 알아낸 조건을 테스트 코드로 남기면 좋습니다. 에이전트가 매번 판단하게 할 부분과, 정해진 단언으로 확인할 부분을 나누면 결과를 비교하기 쉬워집니다.
